Getting started ​

Piwi is a server plus a Playwright reporter. The reporter runs inside npx playwright test and sends the results to the server, which keeps every run with its traces and renders the dashboard. Three steps set up both. What Piwi does says what the server does with those runs: its five jobs, and the pieces around it. New to the vocabulary (run, test case, execution, cluster)? Core concepts defines each term the dashboard uses.

1. Run the dashboard ​

The dashboard is one Node process. Pick the way to run it that fits:

PathBest forNeeds
Desktop appOne developer running Playwright locally, with no server at allAn installer; the runtime is bundled, so no Docker and no Node. Windows x64, Apple-silicon macOS and Linux x86-64; the installers are not code-signed, so the first launch needs a click-through
Docker (below)A shared instance for a team, or anything long-livedDocker; about 300 MB RAM, 1 vCPU, linux/amd64 or linux/arm64, and disk for the traces (sizing)
npx @piwitests/serverA quick local run without DockerNode.js 22 or later; .data/ in the current directory
One-click deployA shared instance with no server of your ownAn account on the host, and what it charges

With Docker:

sh
docker pull phenx/piwitests-server:latest
mkdir -p .data && sudo chown -R 1001:1001 .data # the container runs as non-root UID 1001
# Reachable from this machine only: with authentication off, anyone who reaches the port is an administrator.
# Publish it on every interface (-p 3000:3000) only once authentication is on.
docker run -p 127.0.0.1:3000:3000 -v $(pwd)/.data:/app/.data phenx/piwitests-server:latest
ps1
docker pull phenx/piwitests-server:latest
# Reachable from this machine only: with authentication off, anyone who reaches the port is an administrator.
# Publish it on every interface (-p 3000:3000) only once authentication is on.
docker run -p 127.0.0.1:3000:3000 -v ${PWD}/.data:/app/.data phenx/piwitests-server:latest

The dashboard answers at http://localhost:3000. On Linux hosts the container runs as the non-root UID 1001, which is why the snippet creates .data with the right owner; see Permission issues with volumes if the container cannot write to it. Deployment covers Docker Compose, PostgreSQL and Kubernetes.

The desktop app installs from the latest release. Piwi Runner, below it, is not a dashboard: it runs the tests a team instance asks for, on a machine without the desktop app, which takes the same requests.

With the desktop app, keep it running: a reporter with no server configured finds it by itself. Its URL and access token, for when you need them, are in its Settings → Desktop app under Send results to this app.

Your test project is unaffected by these requirements: Node 22 is the dashboard's requirement, not your suite's, whose reporter needs Node.js 20 or later (Reporter). Want to look around first? The live demo runs in your browser on seeded data.

2. Connect your suite ​

The dashboard's connect wizard, on Home while it has no project and on Settings → Connect a suite after, builds every snippet below from your project name and its own URL, and offers three ways to the same setup: one command, a prompt for a coding agent, or the steps by hand. Each ends in wrapConfig around your config and the capture fixtures in your specs: the reporter entry alone keeps your runs, and those two add the failure screenshots and traces, the network and console capture, and locator healing.

Fast path: one command ​

From your Playwright project, one command installs the reporter, wraps your playwright.config, creates the capture fixtures file and records the connection in .env.example:

bash
npx @piwitests/reporter init --server-url http://localhost:3000 --project my-project

It prints one line per step, + for a file it created, ~ for one it changed, = for one already set, ! for a step left to you:

txt
Piwi setup for "my-project":

  ~ [updated] dependency — Installed @piwitests/reporter
  ~ [updated] config playwright.config.ts — Wrapped defineConfig(...) with wrapConfig(...) and added the import
  + [created] fixtures tests/fixtures.ts — Created capture fixtures — import `test` from here in your specs
  ~ [updated] env .env.example — Recorded PIWI_DASHBOARD_URL, PIWI_API_KEY
  + [created] skill:investigate-failure .claude/skills/investigate-failure/SKILL.md — installed skill
  + [created] skill:apply-locator-healing .claude/skills/apply-locator-healing/SKILL.md — installed skill
  + [created] skill:stabilize-flaky-tests .claude/skills/stabilize-flaky-tests/SKILL.md — installed skill
  + [created] skill:run-the-right-tests .claude/skills/run-the-right-tests/SKILL.md — installed skill
  + [created] skill:write-the-missing-test .claude/skills/write-the-missing-test/SKILL.md — installed skill
  + [created] skill:fix-a-reported-bug .claude/skills/fix-a-reported-bug/SKILL.md — installed skill

Next:
  • If your dashboard has authentication on, create an API key (Settings → Account → API keys) and put it in .env as PIWI_API_KEY: the reporter reads it from the .env next to your Playwright config. Keep .env out of git; in CI, set PIWI_API_KEY as a secret.
  • In your specs, import `test` (and `expect`) from your fixtures file instead of `@playwright/test`.
  • Run `npx playwright test` — the run should appear at http://localhost:3000.
  • For a machine-readable check, set PIWI_OUTPUT_FILE=piwi-run.json and read runUrl from that file after the run.

Every step is idempotent, so it is safe to re-run. When init finds a config shape it will not rewrite, or a fixtures file that already exists, it reports that step as manual with the exact change to make instead of touching the file. Pass --dry-run to preview, or --json for a machine-readable plan that a coding agent can follow to finish the manual steps. init also adds the Piwi agent skills to the project. See npx @piwitests/reporter init --help for all options.

The package is @piwitests/reporter and its command is piwi. Invoke it through the package name, npx @piwitests/reporter <command>, so npx resolves this package: npx piwi would fetch an unrelated piwi package from npm. Once the reporter is a dependency of your project, npx piwi <command> works too.

Then import test from the fixtures file in your specs, the one change init leaves to you:

typescript
import { test, expect } from './fixtures'

A coding agent can do both: the Coding agent path on Connect a suite gives it a prompt that runs init --json, finishes the steps it reports as manual and moves the specs onto the fixtures.

If authentication is on, pass an API key as PIWI_API_KEY; Connect a suite creates one in place. When developers run the desktop app and CI reports to a shared dashboard, add --desktop-app prefer: local runs then land in the app. To wire the reporter in by hand, or to send one run without editing your config, see Reporter.

3. Run your tests ​

bash
npx playwright test

The run streams into the dashboard while it executes, and the reporter prints a View run: link at the end. Open it.

While it runs, the wizard's status line changes from Waiting for the first run to the run reporting, with a link to watch it:

If nothing shows up, read the first lines the reporter prints. This one means it found no server to report to:

txt
[Piwi Dashboard] Not enabled — set PIWI_DASHBOARD_URL or serverUrl to enable.

Set PIWI_DASHBOARD_URL, in the environment or the .env next to your Playwright config, or rerun init with --server-url. From WSL, a dev container or another machine, the URL is the dashboard's address as that machine reaches it, not localhost.

The home page and a project's page leave out partial runs (a run of a few files) until you change their Filters, and a project's page leaves out branches other than the default one too. The Filters block counts the runs it hides, with Include partial runs and Show all branches to bring them back. Your own runs from outside CI (with sign-in off, every run that did not come from CI) stay listed whatever these two filters say, marked with what they would have hidden ("Yours · partial run", "Yours · feature/x"), and not counted among the hidden runs; the charts and pass rates still follow the filters.

In CI nothing Piwi-specific is needed: the same reporter runs inside npx playwright test, pointed at your instance with PIWI_DASHBOARD_URL and PIWI_API_KEY. CI & sharding has the pipeline examples.

Your first failure ​

When a test fails, its execution page opens on what happened, the most likely cause and the next step, with the trace, screenshots and logs underneath. Your first failure, explained walks through one failing test from its headline to its evidence.

Where you write the tests ​

The dashboard is where you read results. Other tools work where you write the tests, in your editor and in your browser:

  • Editor extensions: the Piwi extension for VS Code and the Piwi plugin for the JetBrains IDEs with the LSP API (WebStorm, IntelliJ IDEA Ultimate, Rider). They record a test at the cursor in a browser your project's own Playwright opens, run it and stop it at the editor's breakpoints, and show the latest CI failures at the lines that failed, with the replacement locator as a quick fix.
  • Piwi Picker: a Chrome, Edge and Firefox extension that picks ranked Playwright locators from the page you are looking at and records a flow as a runnable spec. It works with no instance; paired with the editor, it sends a recording to the cursor and follows the editor's runs in its Runs window.

Write, run and fix a test takes a test from an empty spec to a passing run, and names the tool for each step.
