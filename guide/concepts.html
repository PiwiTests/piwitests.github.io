Glossary ​

Every word the documentation and the dashboard use, each defined in a few lines with a link to the page that holds its rule. A word that names two things elsewhere keeps one meaning here, and Words kept to one meaning names the others. New to Piwi? Core concepts reads the dozen words a first run meets, with the object model.

The object model ​

How projects, test runs, test cases, executions and failure clusters hold each other: Core concepts.

Results ​

Project ​

A named container for one suite's results, usually one repository or one suite within it. A project is created the first time results arrive under a new projectName, and carries its own tags, role grants, source control connection, default branch, capability decisions and AI-diagnosis instructions; retention is set for the whole instance (Storage & retention). Its status is the outcome of its latest run, or of its status filter's.

Test run ​

Everything one npx playwright test invocation produced: counts, duration, the HTML report, CI and git metadata, and its executions. One CI pipeline's shards make one run (Sharding), and a run fills in while it goes (Live streaming). A run ran to its end when it passed, failed or hit the global timeout; only such runs count in a project's health. A requested run is one a person asked for from the dashboard and ran on their own machine (Run on my machine).

Test case ​

The identity of a test across time: its project, file, describe path and title. It is created and reused as results arrive, never submitted, so renaming a test or moving its file makes a new one (External test IDs). It is browser-independent: login.spec.ts › signs in is one test case on every browser of your matrix. "This test is flaky" is a statement about a test case. What a run of a test is on its pages: How a result counts.

Execution ​

One attempt of one test case, in one run, on one browser: the error, steps, trace, screenshots and the diagnosis of one failure. A retry is an execution of its own, and so is each --repeat-each repetition. The docs also call it a test-run case. "Here is the stack trace" is a statement about an execution. When a test counts as flaky, failed or interrupted in a run, and how every view reads it: How a result counts.

Pass rate ​

The share of a test's, a run's or a project's results that passed, counted over the results that passed or failed, so skipped tests do not lower it. Every view computes it by one rule, and shows a dash rather than a number when nothing passed or failed: How a result counts.

Flaky rate ​

The share of a test's runs that passed only on a retry, over the same runs the pass rate counts. A file's or a directory's flaky rate reads its tests' runs the same way. The flakiness score and Flake Lab's rate are other numbers: How a result counts.

Baseline (last green run) ​

The earlier run a run is compared with to answer "what changed?": by default the same project's most recent passing run, chosen by environment first, then branch. The Changes tab, the regression signals, the CI gate, pull-request feedback and the AI diagnosis all read it, and so do the environment, visual and page diffs of one failing execution. Which run it is, and what happens when none passed: The baseline. The default and base branches it falls back to: Branches.

New regression, newly flaky ​

What a test did differently from the baseline: a new regression fails here and passed there; a newly flaky test passed here only on a retry and passed at its first attempt there. Both name a change between two runs, not its cause: a newly flaky test can be your change or an old flake. How to tell: What newly flaky says about your change.

Environment ​

A free-text label on a run (production, staging, a preview URL, whatever you use), set with the reporter's environment option or PIWI_ENVIRONMENT. It is a scoping dimension, not a configuration one: flaky analysis, analytics and timeline markers can be narrowed to one environment, so a staging suite's noise doesn't blend into production's numbers.

Environment incident ​

A test run whose failures come from the environment under test being down or broken (staging refusing connections, a host that does not resolve), not from the tests or the code. Piwi flags it when the run finishes, or a person marks it, and leaves it out of the analysis that would blame the tests: see What a flagged run changes.

Tags & ownership ​

Two ways to say what a test is, both declared in the spec file. Tags come from Playwright (@smoke); they slice the test catalog and the flaky leaderboard, and a CI merge gate rule can require one. Ownership metadata comes from piwi: annotations such as piwi:owner: who answers for the test, shown as badges and carried into pull-request feedback. A test with no owner annotation takes its owner from CODEOWNERS. Accepted values and the fallback: Test metadata.

Live runs ​

The words every tool uses for a run while it goes (Follow a run).

Run number ​

A run's id on the instance it reports to, #78, and its page there. The reporter learns it as the run starts and tells it to the editor or the desktop app that follows the run, so every tool links the same page (The run's number and page).

Run name ​

The name a run carries before it has a number (piwiRunRef in its metadata): the one its launcher gave it, an editor's ref or a run request's id, else one Piwi makes up for a run outside CI. A CI run has none: its number names it. See Test metadata.

Worker ​

One of the run's Playwright processes, named by its lane, Worker 2. A worker Playwright starts again after a failure takes the same lane (Worker lanes).

Stop ​

A test standing at a call, waiting to be answered: at a breakpoint, after a step, at a Pause, at page.pause(), or at a failure held for a look. Each tool names it by why it stopped, in the same words (Where a test stopped). A test ended there is skipped (End the test). How the test timeout and the dashboard's durations treat the time paused: Time paused at a stop.

CI position ​

The call a running test of a CI run is at, in your code: a plain, read-only mark at the end of its line in the editors. Never a stop: nothing waits there, and no tool answers it. Which CI runs the editor and Piwi Picker follow: A CI run of your branch.

Hold failures ​

Whether a failed test waits at its line for an answer, in one run. Off, a failure goes on at once, as without Piwi. Some runs start with it on, any tool that follows a run can turn it on or off, and a run nobody attends never holds a failure. Which runs, and what a held test keeps: Hold failures.

Presence, driving a stop ​

Who else is on a run, and who acts at its stop. Each tool says which others have the run open, who watches each worker's page, and who drives a stop. One tool drives a stop at a time, a person or an agent, and a person can take the stop from an agent. How a stop is taken and given back: Who drives a stop.

Watch, Share live ​

Watch shows a worker's page live, in your editor, Piwi Picker or the desktop app (Watch a local test). Share live lets a teammate watch a run on your machine from its page on the team instance (Share a local run live), where a CI run is watched in the live view, every worker at once with Watch all, and a running page read as a document with Inspect. What each sends and keeps is on those pages.

Trace so far ​

A running test's trace up to now, opened in Playwright's trace viewer on the machine the run runs on, with Open the trace so far. The attempt must be traced. Where the button shows and what it needs: Open the trace so far; the desktop app's Inspect, which reads the same trace: Desktop app runs.

Verification ​

A test run several times without retries and without the breakpoints, to see how often it passes (Verify ×3 in the editors). It says how many of its repetitions passed (Passed 3 of 3, Failed 1 of 3) and never holds a failure. How it counts and what it says: When your run ends.

Failures ​

Error fingerprint & failure cluster ​

The error fingerprint is a hash of a failed execution's error with what changes from one occurrence to the next masked out: numbers, ids, URLs, timestamps, an assertion's values. Every failed execution sharing a fingerprint joins one failure cluster, so fifty red tests from one broken endpoint become one cluster you triage once, with a status (open / resolved / ignored) and a note. What is masked, and when clusters merge: How failures are grouped.

Story ​

The one explanation a failure page leads with when several clues (deterministic, rule-based findings) form a known combination: "the Pay button stayed disabled because POST /api/checkout/quote was still in flight", at the strongest member's strength, with every clue folded under it. The combinations, and what leads instead: Clue rules.

Situation ​

The context of a failing execution, on its page: since when it has been failing and whether a newer execution failed again or passed, then the cluster it joins, its status and its issue. It also reads, condensed, in alerts. Each line: Your first failure, explained.

Next step ​

The one recommended action a failure page leads with, chosen by a policy rather than offered as a menu: apply a diagnosed patch, replace a broken locator, reproduce locally, re-run in CI, mark a cluster resolved. Every other action lives in the toolbox. The policy and its order: Fix plans.

Cluster state ​

Where a failure cluster stands, in one sentence with one verb next to a colored dot (still failing, stopped failing, regressed, …). It reconciles the human triage status with what the runs show, and offers the action that closes a gap between them. Every state and which runs count: The state line.

Flakiness score ​

A test case's score from how often it passed only on a retry and how often its status flips across runs, with a root-cause class and an impact ranking by the CI time it wastes. It is a property of the test case, computed over its history, so a test needs a few runs before it can be called flaky. The weights and the classes: Flaky tests.

Flake experiment ​

A piwi flake session on one flaky test: a control arm with no condition, then one arm per suspect, each applying the suspect's condition (a delayed route, another test alongside) with retries off. An arm reproduced the flake when it fails, with the test's own error, significantly more often than the control; a verify experiment reruns that arm after a fix. The verdicts: Flake Lab.

Fix attempt ​

A change a person or an agent reports having made to fix a failure cluster (a patch, a locator edit, a fix plan carried out), on a commit or a branch. It is recorded applied, then verified when the cluster's tests pass on a run that carries it, or regressed when the cluster fails again. See Agent skills.

Locator snapshot ​

What an element looked like when a locator call on it succeeded (role, accessible name, test id, structural anchors), recorded by the capture fixtures and keyed by the call site (file:line) rather than the selector text. When that locator later fails, its snapshots are what Piwi ranks replacement locators from. See Locator healing.

Analytics ​

Metric, dashboard and quality report ​

A metric is a named number with one definition every surface reads (Analytics). An analytics dashboard is a named arrangement of widgets with a default scope (Dashboards); the dashboard alone means the Piwi web app. A quality report is an analytics dashboard rendered as a document, not the run's Playwright run report; a report schedule sends it on a cadence, and each one sent is kept as a report snapshot (Quality reports).

Test Map ​

The Test Map is one graph per project of what the application exposes (pages, controls, links, routes, the handlers and dependencies behind them) and which tests reach each of them. See Scenario gaps & the Test Map.

Reach ​

A test reaches a route, a page, a control or a link when a run observes it doing so: a request to the route, a locator call on the page, a locator that names the control. Triage can record reach too. The route and page gaps are read from observed reach; the code detectors read coverage. Only a trusted test's reach counts in full. The rules: Gap detectors & exposure.

Feature and hub ​

A feature is a product area named by the piwi:feature tag on tests. It groups what those tests reach, and what they miss nearby. A hub is a node most tests reach, such as a session route: it belongs to no one feature. See how features group.

Code reach ​

The application source files a test executed, in the page from Chromium's JavaScript coverage with code reach on, in the backend with server coverage on: observed reach at file level, never line coverage. It feeds impact-from-diff and Uncovered changes.

Coverage ​

Which source code a test ran, per file and runtime (browser or server), at a granularity: the files only, the functions that ran, or the executed lines too. Code reach is its file-level view. A test's coverage is incomplete when part of it could not be collected. The granularities and their cost: Coverage cost.

Coverage report and suite ​

A coverage report is one tool's coverage of one suite's whole run at one commit, attributed to no test. A suite is the tests a report comes from, named when uploading (unit-back), of kind unit or e2e; not Playwright's describe block. The coverage scope decides which files a project's coverage counts. See Combined coverage.

Coverage and the Test Map ​

Two answers to "what do the tests miss". Coverage measures the code: which lines and functions ran, as a ratio; the lines no test or suite ran are lines not run. The Test Map measures the application: which routes, pages and controls the tests reach; what they miss becomes a scenario gap, never a percentage. They meet on the project's Coverage tab and on a file's coverage page.

Uncovered change ​

A changed file of a pull request that no test reached and no suite ran a changed line of. One rule decides it for the pull-request comment, the gate, MCP and the changed, unreached gap. Patch coverage is the same question by line: the share of the changed lines that ran. See Uncovered changes.

Reusable result ​

A test result whose code had already passed unchanged: an earlier pass of the same test ran the same file versions, so the run could have kept that pass instead. A reusable result that failed came from the test, its data or its environment. See Reuse forecast.

Suspect lines ​

The lines changed since a failing test's last passing run that the failing tests executed, read from their coverage, ranked by how few passing tests executed them too. The failure pages, the cluster's diff, the AI diagnosis and the fix plan name them. How they are ranked: Suspect lines.

Locator index ​

The locator chains each test used in its steps, recorded per branch and per Playwright project. It answers which tests use a locator, and it feeds Who uses a locator and Tested elements.

Locator break ​

A locator of the index that a change stops matching: the diff removes or renames a string one of its calls finds the element by. Locator preflight lists them, likely or possible.

Page key ​

A page's URL reduced to its path pattern, ids replaced by placeholders: /orders/123?tab=items and /orders/456 are both /orders/:id, on staging and in production alike. The Test Map's page nodes, the page each locator was used on and Piwi Picker's This page all use it. The rules: What the graph includes; Piwi Picker's path prefixes: URL patterns.

Brittle locator ​

A locator a test uses that breaks on a change unrelated to what the test checks: a position, a styling class, the document structure, a generated id. Piwi judges each locator of the index brittle, watch or stable; see Locator stability rules. Not to be confused with the fragilegap class, which is about the tests reaching a node, not a locator.

Scenario gap ​

A test the suite does not have yet, proposed from the Test Map with its evidence and a next step: a route no test reaches, a control nobody exercises, a changed file no test reaches. A gap is triaged like a failure cluster: accept it, snooze it, dismiss it with a reason, or mark it covered by an existing test (Triage).

Gap class ​

How serious a gap is: blind-spot (nothing exercises it), false-comfort (the tests pass without checking it) or fragile (what reaches it could stop at any time). Server probes report findings instead, unhandled or degraded. What each class covers: Detectors.

Detector ​

A rule that reads the Test Map and the run history and reports one kind of gap, such as declared, never hit or single covering test. Each gap names the detector that raised it; Gap detectors & exposure lists them all.

Exposure ​

How much a gap's node matters, from how often its files change and for how long, whether they were part of an earlier escaped failure, and the priority of the tests that reach it. A gap's score, which ranks it, is its exposure times the detector's confidence. The factors: Exposure.

Probe ​

A re-run of a passing test with one injected fault (a 500, an empty body, a dropped field, a slow response), recording whether the test noticed. A client probe injects the fault at the Playwright boundary; a server probe asks the backend instrumentation to inject it inside the server. A probe run is marked as one (What a probe run never counts).

Declared surface ​

The routes and pages the application says it has, from the instrumentation's route manifest, a committed piwi.manifest.json or an OpenAPI document, as opposed to the ones tests reached. A declared route nothing reaches is a declared, never hit gap (Declared surface).

Page inventory ​

The controls (role and accessible name) and links the reporter records on the pages a passing run visits, so the Test Map knows what a page offers beyond what the tests clicked. Off by default: turn it on with capturePageInventory. What it reads and keeps: What the graph includes.

Map health ​

How complete a project's Test Map is, per input (the page inventory, route handlers, probes, the declared surface, change history…), with the detectors each input wakes. A quiet Gaps view can mean a map that cannot see; the panel names the step behind each input that is short (Map health).

URL pattern ​

A glob over a page's whole address that ties the pages of a site to a project, with an optional environment and branch. Each project keeps its own list, and the browser extension reads them to know which project the page it is on belongs to. See Extension connection.

Access ​

Role and group ​

With authentication on, every account holds an instance role, Administrator or Member. A Member's rights in a project come from the project roles they hold there, granted on one project or on all of them. A group is a named set of users that receives project roles the way a user does. See Access, roles and groups.
