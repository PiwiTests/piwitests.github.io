On this page

All features ​

Everything Piwi does, in one place: what each feature is, what it needs beyond a running reporter, where it lives in the dashboard, and the page that explains it. The groups are the four jobs the product serves (keep the history, explain the failures, hand back a fix, find what your tests miss), then the routes that carry the results to people and tools, and what an operator runs. The docs sidebar and the landing page use the same groups.

New here? Start with What Piwi does and Getting started; this page is the "where next" once a first run has landed. The last two sections list the pieces you install and the decisions a setup involves.

Keep the history ​

CI deletes every report it makes. Piwi keeps every run, trace and report, so "has this always been flaky?" and "did my fix hold?" are answerable at all.

The pieces ​

What you install or reach, how to get each piece, and when you need it.

PieceWhat it isHow to get itWhen you need it
Dashboard serverThe dashboard, its REST API and the MCP server in one Node process. It keeps runs in SQLite (default) or PostgreSQL, and traces, reports and attachments on local disk (default) or S3-compatible storage.The Docker image phenx/piwitests-server (also ghcr.io/piwitests/platform), npx @piwitests/server (Node.js 22+), a one-click deploy template, or the desktop app.Always — every result lands in one. Desktop appThe same server in a native window, bound to 127.0.0.1. It receives your local runs with no URL or token in the config, runs your tests from the window, reproduces a failure or a flake and bisects it in a throwaway worktree, imports a blob report or trace dropped on it, and connects AI assistants to its MCP server in one click.Installers on the GitHub releases page: Windows x64 (.exe or .msi), Apple-silicon macOS (.dmg) and Linux x86-64 (.AppImage, .deb, .rpm). They are unsigned, so the OS warns on first launch.One developer running Playwright on their own machine, with no server to operate.
Live demoThe real dashboard on seeded data, running entirely in your browser — no backend, nothing kept.https://piwitests.dev/demo/Looking around before installing anything.
Reporter@piwitests/reporter, a Playwright reporter that streams each run to the dashboard while it executes: results, errors, steps, traces, screenshots, attachments and the HTML report. The first run under a new project name creates the project (with authentication on, the key needs access to all projects).npx @piwitests/reporter init --server-url <url> --project <name>, or npm install --save-dev @piwitests/reporter and a line in playwright.config. It finds a running desktop app by itself.Always, for live results. Runs recorded before Piwi can be imported instead.
piwi CLIThe command-line tool that ships with the reporter. init wires a project up and skills installs the agent skills; gate fails a CI job on the dashboard’s analysis, select and run resolve and run a saved test selection, and report prints a quality report; preflight lists the test locators an uncommitted change breaks, flake makes a flaky test fail on demand and verifies the fix, bug writes a bug report’s failing test, probe runs the dashboard’s probe plan, codegen turns a Piwi Picker recording into a spec, and ai manages AI-step artifacts.npx @piwitests/reporter <command>. Once the reporter is a project dependency, npx piwi <command> works too; before that, it fetches an unrelated piwi package.Setting a project up, gating merges in CI, checking a change before it runs, reproducing a flaky test, and running only the tests that matter.
Capture fixturesAn extended Playwright test (piwiFixtures) that records network timing, console warnings and errors, Web Vitals, browser dialogs, failure-time ARIA snapshots and the locator snapshots locator healing ranks.A tests/fixtures.ts exporting base.extend(piwiFixtures) — init creates it — with test imported from it in your specs.Recommended: locator healing, slow endpoints, Web Vitals and the richer failure evidence need it.
AI stepspage.piwiLocator() and page.piwiRun() take plain English. Each prompt is resolved once, through the dashboard’s AI provider, into an artifact you commit, and every later run replays it as ordinary Playwright with no model call.Part of the reporter: extend test with extendPiwiAi, then author the missing entries with npx @piwitests/reporter ai resolve.Writing steps in plain English without a model in the loop at run time.
Backend instrumentationPackages for the app under test that, outside production, attach what the server did for each request to its response, so a failing test shows the server’s warnings and errors next to the request that caused them. @piwitests/instrumentation-nitro (Nitro / Nuxt) also sends server spans and the route manifest; PiwiTests.Instrumentation.AspNetCore covers ASP.NET Core, and PiwiTests.Instrumentation.Serilog is its sink for apps that log through Serilog.npm install @piwitests/instrumentation-nitro, or dotnet add package PiwiTests.Instrumentation.AspNetCore (plus PiwiTests.Instrumentation.Serilog when the app logs through Serilog).Your app under test runs on Nitro, Nuxt or ASP.NET Core, and a UI failure may start as a server error.

On any page it picks ranked, stable Playwright locators, flags poor locator targets, suggests assertions, records actions as a runnable spec, and turns a bug you reproduce into a failing test and a report; its DevTools panel adds a locator console, response mocks and viewports. It works on its own; connected to an instance, it also matches your test functions, shows which elements your tests reach, and sends bug reports to the project.The Piwi Picker listing on the Chrome Web Store, which covers Edge and other Chromium browsers.Writing or fixing locators against a live page, or reporting a bug as a failing test.

It reads the reporter’s connection (the environment, the workspace .env or the desktop app); otherwise Piwi: Connect signs in with the browser and creates an API key for the editor.You want CI results where you edit the tests: failures at their lines, heals applied in place, and the tests a change reaches.

Choosing a setup ​

The decisions a team makes once, what happens if you make none, and the page that settles each.

Where should the dashboard run? ​

Default: Nothing runs until you pick one. Details

  • Live demo — Looking around first — seeded data in your browser, nothing kept.
  • Desktop app — One developer on Windows x64, Apple-silicon macOS or Linux x86-64; no Docker or Node needed.
  • Docker — A shared, long-lived instance for a team — the recommended path.
  • npx @piwitests/server — A quick local run where Node.js 22+ is installed.
  • One-click deploy — A shared instance from a template: Railway, Render, Fly.io or Koyeb, or a Compose file for Coolify or Dokploy on a server you already run. Each provisions one container, a persistent volume and authentication on.

SQLite or PostgreSQL? ​

Default: SQLite, created automatically in .data/piwi.db. Details

  • SQLite — Zero configuration; one writer at a time is ample for a team’s test volume.
  • PostgreSQL 14+ — Set PIWI_DATABASE_URL when several dashboard replicas share one database, or database is locked shows up under load. Migrations run on startup either way.

Where do traces, reports and screenshots go? ​

Default: Local disk, under .data/storage/. Details

  • Local disk — No configuration; back the directory up with the database.
  • S3-compatible storage — PIWI_STORAGE_TYPE=s3 with a bucket and region — AWS S3 (static keys optional, instance roles work), Cloudflare R2, DigitalOcean Spaces, RustFS and others.

Turn authentication on? ​

Default: Off: every request is treated as an administrator. Details

  • Off — Only on localhost or in the desktop app.
  • On — Anything reachable from a network: PIWI_AUTH_ENABLED=true and PIWI_AUTH_SECRET, then administrator, reporter and user roles, per-project access, pd_ API keys for CI, agents and editors, and optional Google or GitHub sign-in. Browser sign-in then needs HTTPS (or localhost). Set PIWI_SECRET_KEY too, and work through the production checklist.

Add the capture fixtures? ​

Default: Off: init creates the fixtures file, and each spec opts in by importing test from it. Details

  • Yes (recommended) — Import test from the fixtures file in your specs, and locator healing, slow endpoints, Web Vitals, the console card, the dialogs lane and failure-time ARIA snapshots light up.
  • Not yet — Results, traces, screenshots, failure clusters and flaky scores work without them, and an uploaded trace still yields console, network and the failure-time ARIA snapshot.

Connect an AI provider, and which one? ​

Default: Off. Clustering, flaky scoring, failure clues, locator healing and fix verification need no model. A provider is set in Settings → AI or with environment variables, which win. Details

  • No AI — Everything deterministic still works. A model adds diagnoses with patches, AI-step authoring, the quality-report narrative and, with an embedding model, similarity merging of clusters.
  • Anthropic — The recommended provider: PIWI_AI_PROVIDER=anthropic and PIWI_AI_API_KEY.
  • OpenAI — PIWI_AI_PROVIDER=openai with PIWI_AI_BASE_URL (OpenAI’s own endpoint), PIWI_AI_MODEL and PIWI_AI_API_KEY.
  • OpenAI-compatible or local — Ollama, LM Studio, vLLM and the like: PIWI_AI_PROVIDER=openai with PIWI_AI_BASE_URL pointing at that server and PIWI_AI_MODEL, so nothing leaves your network.
  • Claude Code (local) — The desktop app, or a server with PIWI_CLAUDE_CLI_PATH set, runs the local claude CLI on its own sign-in, with no API key (PIWI_AI_PROVIDER=claude-cli).

Connect source control? ​

Default: No token: runs still carry the branch and commit the reporter detects, and public repositories are read anonymously (rate-limited). Details

  • No token — History, clusters, flaky scores and locator healing are unaffected.
  • A GitHub, GitLab or Bitbucket token — Set instance-wide (Settings → AI → Repository access) or per project. Read access opens private repositories to the diff in AI diagnosis, What changed, uncovered changes and CODEOWNERS ownership. Write access adds pull-request comments and commit statuses (GitHub, GitLab) and auto-heal pull requests (GitHub, GitLab, Bitbucket Cloud), both with PIWI_SITE_URL set, and CI re-runs from the dashboard.

What should block a merge? ​

Default: Playwright’s own exit code: any failed test. Details

  • The exit code — You only need "did anything fail".
  • piwi gate — The dashboard’s analysis decides: how many tests failed, newly failed, newly turned flaky or are quarantined, a failure cluster never seen before, required tags, or a selection whose tests must run and pass.

Which MCP tools should agents see? ​

Default: Every tool whose capability is not declined. Details

  • All — The agent can reach every part of Piwi.
  • ?modules=core — Append to the MCP URL (any comma-separated set of core, workflow, healing and agents) to narrow the list for a tighter token budget; it never re-enables a declined tool.
  • Decline a capability — Declining one on the Setup page, or a whole module in its presets, drops the tools that depend on it for every client; tools that need no capability stay.

How much history to keep? ​

Default: Every run: run pruning is opt-in. Details

  • Everything — The history is the point; budget disk for traces and reports.
  • PIWI_RETENTION_DAYS — A nightly sweep deletes older runs with their files. Kept runs stay, PIWI_RETENTION_MIN_RUNS keeps each project’s newest runs, and pruned runs stay counted in the analytics rollups.

Start from history you already have? ​

Default: Trends start with the first reported run. Details

  • Start fresh — Nothing to import.
  • Import — An administrator backfills from Playwright blob reports or bare trace files with the project’s Import button, or drops them on the desktop app; imports are idempotent and send no notifications.
