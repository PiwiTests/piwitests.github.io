Notification events & webhooks ​

A subscription picks one or more of these events. This page lists when each one fires and what a webhook channel receives; channels, subscriptions and delivery are on Notifications & alerts. Some runs fire none of them: a run from an editor, a Flake Lab or probe run, a partial run from a developer's machine, and the others that send nothing. A run flagged as an environment incident fires environment.incident in place of the events its row names.

Events ​

EventFires when
run.finishedA run completes (any status)
run.failedA run completes with failures, or stops at Playwright's global timeout (status: "timedout")
run.failed.default_branchA run fails, as run.failed reads it, on the repository's default branch
run.interruptedA run stops reporting before its end and the stale-run sweep marks it interrupted (two minutes without activity, an hour for a run still in its global setup or with a shard still in its own, and an hour for a sharded run waiting for a shard that has not started, once every shard that started has ended; each counted at the earliest from when the server could be reached again, after a restart or a database outage). The payload is a run event's, with status: "interrupted" and the results stored so far; Flake Lab and probe runs send none
cluster.newA new failure cluster appears in a run that ran to its end (passed, failed or timed out). A cluster first seen by a run that sent no notification of it (a run from an editor, a partial run from a developer's machine, an import, a cancelled or interrupted run) is announced by the first such run that sends notifications, unless the cluster is resolved, ignored or snoozed when that run ends, or its first run was deleted. When runs overlap, the first to end announces it and no other run does, whether or not a channel is subscribed
cluster.fixedA run passes every test a cluster covers: the fix landed (a filtered re-run of just those tests counts). The payload's verification says whether the diagnosis was corroborated (diagnosis-verified) or the tests merely stopped failing, and resolved whether the triage status was closed automatically
cluster.regressedA cluster with a recorded fix fails again, or one resolved by hand fails in a run started after it was resolved (no fixLandedRunId then); reopened says whether a resolved cluster was set back to open
flakiness.spikeA completed run contains flaky tests; the flakiness-threshold filter keeps only rates above N%
perf.regressionA run is at least 20% slower than the median of the previous five complete runs on the same branch and environment (runs of the whole suite: no partial, Flake Lab, probe, bisect or reproduction run, and no environment incident); the regression-% filter raises the bar
diagnosis.completedA diagnosis of a cluster, or of one of its failures, is stored: Piwi's (requires an AI provider) or one an agent records. A failure in no cluster sends none
auto_heal.pr_openedAuto-heal opened a pull request; the payload carries prNumber, prUrl, branch and editCount
environment.incidentA completed run is flagged as an environment incident; it replaces the run's run.failed, run.failed.default_branch, flakiness.spike, perf.regression, cluster.new and bug.looks_fixed (run.finished still fires). The payload carries rule, reason, host, otherProjects and incidentKey, which is the same for every run of one outage across projects, so a channel receives one message. A subscription filtered on owners does not receive it
test.stuckA running test of a live run has run longer than both two minutes and three times its longest duration among its last ten passing executions (Stuck tests), once per attempt; a run started on a developer's machine (origin local, desktop, editor, preflight or bug) sends none, complete or not, and neither does a run that sends no run event
bug.looks_fixedA test.fail() test passed in a completed run, in every browser project that ran it, and did not already pass on the previous completed run of the same branch that sends notifications itself; the payload lists the tests, each with the bug report (bugId, from piwi:bug) and ticket (link) it names

report.ready needs no subscription: a report schedule sends it to the channels it names, through the same outbox. Its webhook body adds the whole report: { "event", "payload": { "snapshotId", "scheduleId", "periodEnd", "url" }, "bundle", "timestamp" }.

Webhook body ​

A webhook channel receives a POST with the body { "event": "run.failed", "payload": { … }, "timestamp": "…" }. For run events the payload includes up to three failing tests, so you can act without a round-trip to the dashboard:

json
{
  "event": "run.failed",
  "payload": {
    "runId": 42,
    "projectName": "checkout",
    "status": "failed",
    "totalTests": 120,
    "failedTests": 3,
    "passedTests": 114,
    "flakyTests": 2,
    "skippedTests": 3,
    "didNotRunTests": 0,
    "interruptedTests": 0,
    "failingTestCount": 3,
    "branch": "main",
    "environment": "staging",
    "commit": {
      "sha": "3f9c2a1d8e7b6c5d4e3f2a1b0c9d8e7f6a5b4c3d",
      "message": "Validate the card number before enabling Pay",
      "author": "Alex Martin",
      "url": "https://github.com/acme/checkout/commit/3f9c2a1d8e7b6c5d4e3f2a1b0c9d8e7f6a5b4c3d"
    },
    "ciUrl": "https://github.com/acme/checkout/actions/runs/123",
    "origin": "ci",
    "history": [
      { "runId": 40, "status": "passed", "failedTests": 0 },
      { "runId": 41, "status": "passed", "failedTests": 0 },
      { "runId": 42, "status": "failed", "failedTests": 3 }
    ],
    "topFailures": [
      {
        "title": "applies discount code",
        "suitePath": ["Checkout", "Payment"],
        "filePath": "tests/checkout.spec.ts",
        "line": 38,
        "browserName": "chromium",
        "owner": "@acme/payments",
        "headline": "getByRole('button', { name: 'Pay' }) never became enabled, click timed out after 30 s",
        "errorExcerpt": "TimeoutError: locator.click: Timeout 30000ms exceeded.\nlocator resolved to <button disabled>Pay</button>",
        "source": {
          "file": "tests/checkout.spec.ts",
          "line": 42,
          "snippet": "    41 |   await page.getByLabel('Code').fill('SAVE10');\n>   42 |   await page.getByRole('button', { name: 'Pay' }).click();\n    43 | });"
        },
        "history": ["passed", "passed", "failed"],
        "testCaseId": 815,
        "executionId": 9001
      }
    ]
  },
  "timestamp": "2026-07-11T10:00:00.000Z"
}

headline is the one-line explanation the dashboard builds from the Playwright error (the locator, its last state, the expected and received values, the timeout; see Failure evidence), absent when the case carries no error. errorExcerpt is the error's message head: at most five lines before the call log and the stack trace, capped at 300 characters, plus the last waiting for … line when the head is only a bare timeout. Slack and email messages lead with the headline, quote the excerpt and link each failure to its execution. The pull-request comment quotes failures the same way.

A test is failing when the last attempt of one of its repetitions failed: a test that passed on a retry counts as flaky, never as a failure. interruptedTests counts the tests the run's interruption cut short, in none of the other counts. topFailures names the first three, failingTestCount counts them all, each test once per Playwright project however many of its --repeat-each repetitions failed (failedTests counts each failed repetition), and owners covers every failed attempt, so a team hears of its flaky test's failed first attempt. Each failure names its describe blocks (suitePath), the line it is declared on, its Playwright project (browserName) and its owner. source holds the lines around the line the failure threw at, as the reporter captured them: the test file, or the helper the error's stack points at, from four lines before it to two after, the failing line marked >.

origin is what launched the run: ci, local, desktop, … (run origin).

history lists the run and up to nine runs before it on the same branch and environment, oldest first: the ended runs that would send notifications themselves (which runs send none, an environment incident included). Each failure's history gives that test's outcome in each of those runs (passed, flaky, failed, skipped, didnotrun for a test that did not run, interrupted for one the run's interruption cut short, in no outcome, or null when the run did not report it). commit comes from the run's Git metadata, linked when the project's repository host is known, and ciUrl from its CI metadata.

Emails ​

Every event has its own email. A run's email opens with its outcome in large type, then a bar of its tests by outcome, its history as a row of squares with what it says (First failure after 6 passing runs), the commit and the CI build. Each failure in topFailures shows its full name with its describe blocks, its file and line, its source syntax-highlighted with the failing line marked, its error with the expected and received values in color, and its own history, which tells a new failure from one that keeps coming back. A digest lists each event with its run's outcome bar.

Slack and Microsoft Teams ​

A Slack message heads with the email's headline and keeps the rest in an attachment whose side stripe takes the event's color: the run's tests by outcome and its history as rows of colored squares, the commit, the CI build and the owners as fields, then each failure with its describe blocks, its file and line, its source with the failing line marked, its error and its own history, and buttons to the run and the build. A Slack-compatible server (Mattermost, Rocket.Chat) shows the message's text line, and none of its blocks.

A Microsoft Teams card sets the headline on a band of the event's color and draws the outcomes as a stacked bar chart. Each failure's code goes in a code block Teams colors by language, and its error's expected and received lines are green and red. Where a Teams client draws no chart or code block (the mobile app), the card shows the same squares and numbered lines instead.

Payload fields by event ​

Every event that comes from a run carries that run's branch and environment when the run reported them: the run.* events, flakiness.spike, perf.regression, the cluster.* events, bug.looks_fixed and test.stuck. A subscription's branch and environment filters match on these two fields.

  • Run events (run.*, flakiness.spike, perf.regression): the run, its counts, topFailures, and the owners of the failing tests. perf.regression adds durationMs, baselineDurationMs and regressionPct.
  • cluster.new: the cluster's signature and title, sampleErrorExcerpt (cut like errorExcerpt), affectedCases, the owners of the tests that failed into it in that run, and firstSeenRunId when it first appeared in an earlier run, which sent no notification of it.
  • cluster.fixed and cluster.regressed: the cluster's signature, title and the runId that decided the verdict; for a fix, the commit and timeToResolutionMs. With an SCM token, a fixAuthor object ({ name, email }) names the author of the fixing commit (for a regression, of the fix that did not hold). A fix landed by an auto-heal PR carries healPr ({ number, url, actionId }).
  • diagnosis.completed: the cluster, and the diagnosis's summary, rootCause, category and confidence. A diagnosis of one failure in the cluster adds its executionId, and the notification opens that failure.
  • test.stuck: the run, the test's testTitle, suitePath and location, the browserName, shardIndex and worker it runs in (parallelIndex, its lane from 0, which the message shows from 1 as worker 2, absent from an older reporter; workerIndex, Playwright's worker process), the attempt's startedAt (epoch ms), elapsedMs (how long it had run) and usualMs (its longest passing duration), and the test's owners.

A cluster.* event also carries knownIssue ({ key, url }) when the cluster is linked to a tracker issue.

Verifying a webhook ​

When the channel has a secret, each request carries an X-Piwi-Signature header, so you can verify that Piwi sent it. Its value is sha256= followed by the hex HMAC-SHA256 of the raw request body, keyed with the secret:

X-Piwi-Signature: sha256=5d41402abc4b2a76b9719d911017c592...

To check it, compute the HMAC over the exact bytes you received, never a re-serialized payload, and compare the two in constant time. In Node.js:

typescript
import { createHmac, timingSafeEqual } from 'node:crypto'

function isFromPiwi(rawBody: Buffer, header: string | undefined, secret: string): boolean {
  const expected = Buffer.from(`sha256=${createHmac('sha256', secret).update(rawBody).digest('hex')}`)
  const received = Buffer.from(header ?? '')
  return received.length === expected.length && timingSafeEqual(received, expected)
}

A channel with no secret sends no header. Webhook secrets are encrypted at rest.
