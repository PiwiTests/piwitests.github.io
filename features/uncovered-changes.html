Uncovered changes in pull requests ​

NeedsReporterSCM token

A pull request that changes server/api/orders/[id].patch.ts while no test ever requests that route passes CI and proves nothing about the change. When a run finishes, Piwi joins the files its change touched to the tests that observably reach them, and names the changed files nothing reaches: the uncovered changes. Each one is a changed, unreached scenario gap. Its draft starts from the route or page the file serves, or the nearest one a test reaches under the same path, with that test named. When the head commit has combined coverage, the same section counts the changed lines too, and names those no suite ran, in every file.

One rule for every changed file ​

The comment, its commit status, the gate, the MCP tool and the changed, unreached detector read one rule. A changed file is:

ReachWhenCounted
Reacheda test of this run reached it, or a suite of the head commit's coverage ran one of its changed linesyes
Reached earlierno test of this run did, but a test of the project's last 30 runs did: a run narrowed by a selection, not a missing testyes
UnreachedPiwi can observe the file, and nothing above reached it: an uncovered change, and a changed, unreached gapyes
Not observablenothing maps the file to a test, so nothing can be said either wayno
Out of scopethe project's coverage scope leaves it out: tests, build output and generated code by defaultno
Deletedthe change removed itno

A test reaches a file when it:

  • requested a route or visited a page the file serves, matched by the framework's file naming (server/api/**, server/routes/**, Nuxt pages/**);
  • ran a step whose locator is written in the file (a page object, a helper);
  • executed one of the file's functions, with code reach on.

Piwi can observe a file when one of these could happen to it, or when the head commit's coverage counts its changed lines. A skipped test reaches nothing. A changed, unreached gap closes when a later diff no longer counts its file as uncovered, or when the Test Map's next recompute finds it reached or out of scope; an accepted one closes only once a test reaches the file.

Before the pull request, the editor extensions mark the lines of an uncovered change of a page or a server route in the file itself, by a rule of their own: no coverage scope, no window of runs, and a page counts as reached only when a test's locator acted on it.

The diff comes from the source control connection. A run of a pull request is compared with the branch it merges into, so every push reports the whole pull request: the one its CI names, else the one open on its branch, so a push-triggered workflow reads its pull request too. Any other run is compared with the commit of the last passing run. A public repository is read without a token, so its uncovered changes and their gaps appear in Piwi, though nothing is posted; a private one needs a token. With no diff, nothing appears.

On the pull request ​

With pull-request feedback turned on, the comment gains an Uncovered changes section. The uncovered changes come first, grouped by ticket (read from the commit messages and the pull request):

md
#### 🟣 Uncovered changes · 3 of 7 files · 2 tickets
Changed files no test reached, in this run or the last 30 runs. Observed reach, not instrumented coverage.

**PROJ-418**
- `server/api/orders/[id].patch.ts` · changed (+41 −3) · 0 tests in 30 runs
  → [open its gap](https://piwi.example.com/projects/4?tab=coverage&gap=31): **Accept** copies a draft test

When the head commit has combined coverage, the section also counts the change's lines that can run (its patch coverage), and names the changed lines no suite ran in the files a test did reach: a test visiting a file is not a test running the change.

md
**Patch coverage 82.9%**: 34 of the 41 changed lines ran (unit 28, end to end 19), at `a1b2c3d`.

**Changed lines no suite ran**
- `api/Orders/OrderService.cs` · 7 of 12 ran · not run: 14 to 18, 40

The section ends with what it did not count: Not counted: 2 files Piwi cannot observe, 1 file outside the coverage scope.

Three more detectors read the whole pull request at each run: an error status a route's handler gains that no run answered with, a control a page gains, and a title no test's words match (the detectors). Their gaps carry the pull request's number, close when a later run no longer raises them, and the section counts them with a link to the pull request's gaps, where the change-coverage status leads too.

A coverage report uploaded for the commit after the comment, or the run's own coverage arriving after it, posts the comment again a few seconds later; a later push's comment is never overwritten by an earlier commit's.

When commit statuses are on too, a second status joins the run's own: piwi/tests/change-coverage with the default status context, described as 3 of 7 changed files no test reached, with the patch coverage when there is one. It is always success, so it informs a reviewer without blocking the merge, and it leads to the pull request's gaps on the Coverage tab.

The files no test reached are the Test Map's part: they are left out while the changed, unreached detector is muted on the project, or where the Test Map is declined. The changed lines are coverage's part and stay either way.

From an agent ​

The get_change_coverage MCP tool returns the same join for a run or for an explicit base and head commit, grouped by ticket, without recording anything: each file's reach, its lines when the coverage counts them, and the files not counted. The write-the-missing-test skill takes it from there. The REST endpoint is in the API docs.

The gate flags ​

Two flags of piwi gate read the same rule, one per form:

  • --max-uncovered-changes <n> warns when more than n changed files are uncovered changes (the file form);
  • --min-patch-coverage <percent> warns when fewer of the changed lines ran, or when the head commit's coverage names none of them (the line form). Run it after the unit-test jobs uploaded their reports.

Both are warn-only: they never change the verdict or the exit code, because the numbers inform rather than prove. The first names up to five of the files, and a stored evaluation keeps its warnings. Either warns too when the run has no source control diff to count. Without them, the gate ignores uncovered changes.

Limits ​

  • Observed reach, then lines. Without coverage, a reached file may still hide an untested branch; with it, the changed lines no suite ran name it. An unreached file may be dead code.
  • Naming conventions. Files map to routes and pages through Nitro and Nuxt file naming; other frameworks rely on locators, code reach and coverage, so without those more of their files are not observable and not counted.
  • Ten files listed. The comment names at most ten files per list and counts the rest.
