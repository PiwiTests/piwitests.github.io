Slow tests & wasted time ​

NeedsReporterCapture fixtures

The test list tells you what failed; it doesn't tell you where the minutes go. This page covers the project's Performance tab (duration trends, the slowest tests, timeout opportunities, slow endpoints) and the time Piwi counts as wasted. What the run cost the machine is on CPU, memory & disk; flaky tests ranked by the time their retries cost, on Flaky tests.

Duration trends ​

Average and P90 duration over time, so a few slow outliers don't hide a real regression (a rising P90 with a flat average is a tail getting worse). Read the percentile, not the average: a handful of slow outliers move it and barely move the mean, and the outliers decide how long a shard takes. Slowest tests ranks the top offenders by duration.

Timeout opportunities ​

Tests whose configured per-test timeout dwarfs their real p95 duration — so a hang or failure waits far longer than it needs to — plus tests still carrying a stale test.slow() mark they no longer need. Each row suggests a tighter timeout (or removing the mark) and the time reclaimable per failing run, ranked by impact.

An oversized timeout costs nothing while the test passes and its whole budget each time it fails: a thirty-second timeout on a three-second test burns twenty-seven seconds on every failure before anyone learns anything.

This reads the per-test timeout the reporter captures; runs reported before that shipped still surface stale test.slow() marks from annotations and durations alone. The thresholds are set in Settings → Performance.

Wasted time ​

Wasted time is time that produced no signal. Piwi counts two kinds:

  • Waits: the time inside wait steps that match the wasted-wait patterns. By default only explicit sleeps count (waitForTimeout and friends), since framework-injected waits (load-state, wait-for-function) are usually unavoidable. Tune the patterns in Settings → Performance, or lock them with PIWI_WASTED_WAIT_PATTERNS; * counts every wait, which shows once how much of the suite is waiting. They are applied when a run is viewed, so a change re-classifies the whole history with no re-run.
  • Failed attempts: the time spent running attempts that ended failed or timed out.

A run's test list and an execution's Details popover show each test's fixed-wait time, and the run's Timeline tab draws the sleeps as bars with Show waits. The Wasted CI time Analytics widget adds waits and failed attempts over time and per project, beside CI time, the minutes the runs consumed, and states how much is reclaimable by tightening timeouts and dropping stale test.slow() marks. With a cost per CI minute set, each wasted-time number carries its cost.

The flaky list's wasted CI minutes are a narrower number, a test's retries times its average failed attempt: see Impact ranking.

Time paused at a stop ​

When a test stands stopped at a breakpoint, a Pause or a held failure, its duration leaves the time paused out, while every step keeps its clock time: the timelines draw each stop as a Paused band, and the step statistics (the slowest step, wasted time) leave it out.

The test timeout stops while a test is paused at a breakpoint, and so does the paused call's own budget (actionTimeout, or expect.timeout for an assertion on that line). A wait the test started before the stop keeps its own deadline: expect.poll, toPass, or a waitForRequest, waitForResponse or waitForEvent around the paused call can run out while you look and fail the test. The pause bar then goes away, before Playwright's failure screenshot and the afterEach hooks.

Network and Web Vitals ​

  • Slow endpoints — slow API calls grouped by method and normalized route (e.g. /users/:id), for a run picked from the tab.
  • Browser Web Vitals — TTFB, DOMContentLoaded, FCP and more, with color-coded thresholds, shown per execution in the Performance tab of the execution page's evidence rather than on the project.

Both require the capture fixtures in your test setup — without them the reporter has no network timings or Web Vitals to aggregate.
