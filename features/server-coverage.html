Server coverage ​

With an ASP.NET Core backend built for coverage, each test records the backend code it ran: its files, the functions that ran in them and, at the finest granularity, the executed lines. Requests are told apart, so tests running in parallel against one shared backend each keep their own. The browser side is code reach; both feed the execution page, the file coverage page, the editors and the coverage insights.

Turn it on ​

  1. Add the PiwiTests.Instrumentation.Coverage package to every project whose code you want covered, as its README shows, serve it with app.UsePiwiTestLogs() (backend instrumentation), and build the test environment with -p:PiwiCoverage=true. Never ship that build to production: its code runs slower, and its coverage endpoints expose source paths and line numbers. It refuses to start in the Production environment, and PiwiCoverageForbidden makes a build fail when coverage reaches it (README).
  2. Set the reporter's coverage.server option, or PIWI_COVERAGE_SERVER, with the capture fixtures in place.
ts
reporter: [['@piwitests/reporter', { coverage: { server: 'lines' } }]],

Against a backend that is not a coverage build, no response names any coverage, so the reporter collects nothing and the option costs nothing: it can stay on, and the build decides.

What it records ​

coverage.serverRecords per test
filesthe backend files that ran, paths only
functionsalso the start and end line of each function that ran
linesalso the executed lines

With functions and lines, each file names the git blob its line numbers refer to. At the end of the run the reporter also sends each backend's run-level coverage, attributed to no test, with each file's executable lines at lines: the lines no test runs, in every assembly built with coverage, including those whose code never ran. A test whose coverage the backend no longer held, or that could not be collected, is marked incomplete.

The backend names the checksum of the source each file was compiled from. When the file in the reporter's checkout differs (the backend was built from another commit), the reporter keeps the file's path but drops its line numbers, which would point at the wrong lines, and marks the test incomplete; the run-level coverage drops them the same way.

How it is collected ​

Each response names its request's coverage in an X-Piwi-Coverage header. Once the test ends, outside its time, the reporter asks each backend origin for the coverage its pages and API calls named, several tests per call. The run-level coverage is read as the run's last test ends, while a Playwright webServer is still up, and the lines and functions the tests' coverage named are added to it. Every answer names the backend process: a random id, which also starts each request id, and when the process started. The run-level coverage is whole only when the process that answers it is the one that served the run's first requests.

Limits ​

  • Run level only: lambdas created at startup (inline minimal API handlers, inline middleware, DI factory lambdas), work outside a request (hosted services, timers), and work a request started that still runs once the reporter collected its coverage. The methods they call count normally.
  • API calls through Playwright's request fixture keep their last response's coverage only: a redirect's earlier responses, and a response failOnStatusCode turns into an error, name none.
  • One backend per request: a call the backend makes to another counts there only if it forwards the X-Piwi-Coverage header.
  • A restart during the run: the new process starts with no coverage. Each test's lines are kept, from its own coverage; what the earlier process ran outside a request (startup, background work) is lost, and a test whose requests it served but the reporter had not yet collected is marked incomplete. The reporter warns, the run's header reads Coverage incomplete: the backend restarted during the run, and the run's coverage in the API names the origin and about when it restarted. A backend unreachable at the end of the run is flagged the same way, with only the tests' lines kept. The commit's combined coverage notes the run, and its e2e suite reads as incomplete unless a complete run of the commit counts beside it.
  • Exclusions: the coverage build leaves out what coverlet does, read from the project's coverlet settings (README): an excluded member has no executable lines and no coverage.
  • C# and Visual Basic only.

Cost ​

On a large ASP.NET Core and Vue application, the coverage build alone ran within 1% of a normal build, and per-test line coverage added under 10% to its UI tests, with no measurable change in its CPU. The build records the same way at every granularity, so files and functions cost what lines cost. Coverage cost has every mode, how it was measured, and the prototype figures.
