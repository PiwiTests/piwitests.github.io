Runs from the editor ​

NeedsEditor extension

The editor extensions run your tests where you edit them, then show a run's progress in the status bar and its results over the latest CI run's failures.

Run tests ​

  • The lines above a locator line, an application file or a page file (CodeLens in VS Code, Code Vision in a JetBrains IDE) run the tests they name when clicked; those of a server file record its coverage.
  • Piwi: Run the test at the cursor (Ctrl+Shift+Alt+K, Cmd+Shift+Alt+K on macOS) runs the test whose test(…) call holds the cursor, and Piwi: Run this spec every test of the spec; both in the editor's Piwi submenu on a spec and under VS Code's editor title Run button (the caret in a JetBrains IDE), saving the spec first. Run in VS Code's test hover runs it, as the Testing view does. A test the instance does not know, such as one just recorded, runs by the line of its test(…) call, with or without an instance.
  • Piwi: Verify the test at the cursor ×3 (Verify the test at the caret ×3) runs that test three times as a verification.
  • Piwi: Run the tests that reach this file runs every test reaching the active file through code reach; also in the editor's and the file tree's Piwi submenu.
  • Piwi: Run a saved selection… runs a selection.

The command, npx playwright test with the arguments piwi run would pass, runs from the Playwright config's folder: as a task in VS Code, in a terminal of its own (Tasks: Rerun Last Task restarts it), in the Run tool window in a JetBrains IDE (Rerun restarts it), or in the IDE's Playwright runner (test tree, Debug, Rerun Failed Tests), a choice of Settings → Tools → Piwi that keeps every control of a Piwi run, through the runner's Rerun and Debug too. It sets PIWI_ORIGIN=editor and its own PIWI_ORIGIN_REF (run origin), by which the editor finds its run. Breakpoints and the editor pause it: Pause and step from the editor.

How a run starts ​

Two choices apply to every run: Run headed (--headed, a verification included) and Hold failures Auto, On or Off from the run's start. Auto lets Piwi decide: on with your breakpoints or a page.pause(), headed for the latter. Piwi: Turn headed runs on or off and Piwi: Hold failures from each run's start… set them (in VS Code, piwi.runHeaded and piwi.runHoldFailures, shown in the status bar's tooltip and offered together by Piwi: Run options…). A debug run, a Flake Lab line and a fix plan's check leave them out.

The Testing view (VS Code) ​

VS Code's Testing view lists Piwi's tests: the specs your instance knows, as they stand in the editor, under their folders and test.describe blocks, each test with its latest result and duration, and why and where a failure failed (Peek Error). The results are published as a test run (Piwi: run #120 on main) whenever the runs it shows change, and a run in progress is one of its own, each test shown as it begins and ends. Its gutter shows each result in place of Piwi's icon; the line keeps Piwi's hover. The view has no flaky result, so a flaky test shows as passed, and its line ends with flaky. An item is named by its test's title alone, as a screen reader reads it, and the view's filter finds tests by @piwi:flaky, @piwi:quarantined, a Playwright tag (@piwi:@smoke) or an owner (@piwi:owner:ada). With the view off, Piwi's gutter marks a test with no recent result with a dashed ring.

Each test's actions are one list in both editors: Run with Piwi, Debug with Piwi and Verify ×3 with Piwi, a failure's trace and screenshot, Open in dashboard, Copy context for agent, then the test's Flake Lab commands. In VS Code, Piwi: Show the test's actions… opens them from the Testing view's gutter and its menus, the line number's menu with the view off, and More… in the test's hover; in a JetBrains IDE, either click on the result icon.

Run with Piwi, the view's run profile, runs the tests you pick as the commands above do, one command per Playwright config with your breakpoints, Debug with Piwi runs them headed, holding each failure at its line, and Verify ×3 with Piwi runs them three times. From a failed test's actions, Debug with Piwi runs it as Debug in my editor does, stopping once at the line it failed through, with no question. Tests show running as they begin, offline too. A test the run gave Piwi no result for, such as one the instance does not know, passes when the command exited with 0, else is an error. The view shows results; it does not discover tests, and its Debug runs Piwi's run control, not a debug session: a spec the instance has not seen joins the tree once you open it. piwi.testExplorer turns the view's Piwi tests off.

Re-run the failing tests ​

Piwi: Re-run the failing tests (Ctrl+Shift+Alt+F, Cmd+Shift+Alt+F on macOS; Tools → Piwi → Re-run the failing tests) runs every test still failing, or edited since its run, one command per Playwright config, or those of one config from its node in the failures view; when none fails, it says so.

After a run ​

Within a second of a run of the project ending, the editor reads the branch's latest run and its failures again, told by the instance's event stream; else every five minutes with the stream, every minute without. A checkout or a commit is noticed within seconds: the editor reads that run again and compares your application files with the new HEAD.

A run started from the editor is its own wherever it runs: the status bar follows it, the gutter shows each test as running, then its result, and its failures read your run #124 once it ends. The editor learns the command's end and exit code from the process it started, in every shell, a rerun included. When no run on the instance carries its ref, it says why: its reporter sent nothing (its lines in the output name the server address, the key, or a refusal), or the config has no Piwi reporter: The run ended (exit code 1) but did not reach https://piwi.example.com: is the Piwi reporter in the Playwright config?

When your run ends ​

Once a run you started from the editor is read, a notification (a balloon titled by its run in JetBrains) says what it changed: Piwi: run #124 · 1 of 3 CI failures fixed, 2 still failing (login.spec.ts › logs in, checkout.spec.ts › pays) and new failures, with Open the failures, Open in dashboard and Re-run failing. The piwi.runNotifications setting (Settings → Tools → Piwi in JetBrains) shows it when a test fails, the default, always (a passing run then offers Only on failure), or never; Settings opens it in VS Code.

A CI run of your checked-out branch says the same once it ends, against the run it replaced: Piwi: CI run #130 on feature-x · 2 fixed · 1 new failure (cart.spec.ts › adds). The piwi.runNotificationsScope setting, The runs it says it for in JetBrains, keeps it to the runs you started.

A verification, Verify ×3, runs the test three times without retries or breakpoints (--repeat-each=3 --retries=0), each run a result on the instance, and holds no failure. Its notification says how many passed, whatever the setting: Piwi: run #124 · Passed 3 of 3, or Failed 1 of 3 with Open the failures and Open in dashboard, counted from the results the run streams (Failed at least 1 of 3 when some were missed), else from its exit code. Like a fix plan's verification and a Flake Lab line, it is listed, paused and stopped as any run.

A test that waits for you ​

A test held at its failure, or stopped at page.pause(), while the editor is in the background, calls you once: a notification with Resume and Go to the stopped line in VS Code, the system's attention request (a bouncing or flashing icon) in a JetBrains IDE, which also comes to the front while you are in another application and the debugger's Focus application on breakpoint is on, as it is by default. A stop you asked for, at a breakpoint, a Step or a Pause, never does, nor one an agent drives or a desktop app's job, which calls from its own window. A paused run has the controls.
