Locator healing ​

NeedsReporterCapture fixtures

When a locator stops matching (a button was renamed, an element moved, a hashed class changed), Piwi suggests ranked replacements, captured from the last run where the test passed. Healing is read-only: it never rewrites your test. Auto-heal PRs is the separate, opt-in feature that opens the fix as a pull request.

What it does ​

While tests run, the capture fixtures record a locator snapshot for each successful action or passing web-first assertion (a passing expect(locator).toBeVisible() proves the element resolved just as a click does): the target element's attributes, plus alternative locators ranked by a stability score (data-testid = 100, role + accessible name ≈ 90, semantic CSS ≈ 35–40, hash-suffixed ≈ 10). Capture also generates rename-proof alternatives: locators scoped to a stable ancestor (getByTestId('signup-form').getByRole('textbox') ≈ 72, a unique landmark ≈ 55) and a name-free getByRole when the element is the only one of its role. Each candidate is checked against the live page: an ambiguous test id, id, name or class is dropped, and an ambiguous role, text, placeholder, alt or title candidate ranks below every unique one. Input values are never captured.

When a locator later fails, the server looks for replacements, most trustworthy first:

  1. Diff rename: the run's own diff renamed the string the locator finds its element by, at this call site, as Locator preflight predicts it with a likely break. The replacement is the same locator with the new string, and the panel says where: "“Pay now” became “Pay” in CheckoutButton.vue:14". It needs a run with a diff (a pull request, or a commit after a passing run) and a source-control token. Its edit replaces the string inside your quotes, and an auto-heal PR can use it.
  2. Prior run: the same call site (file:line:col, or file:line when only the column moved) had a passing snapshot.
  3. Fingerprint: the call site moved lines, but the locator matches a prior snapshot.
  4. Cross-test: another test in the project captured the same locator.
  5. ARIA fallback: no snapshot exists, so limited suggestions come from the failure-time ARIA snapshot: elements sharing a word or the role with the failing locator.

A snapshot found by rungs 2 to 4 is then checked against the failing page's ARIA snapshot. When the element is gone under its old name and a confident match exists, fresh locators for the element it most likely became replace the stored ones (an element match), matched by role, heading level and, on a total rename, its position among elements of the same role.

The recommended fix ​

A single recommended fix is highlighted. It follows the failing locator itself, not the rest of your suite: among the alternatives with a stability score of 50 or more, the most stable that uses the same method as the failing locator's last call (getByLabel for getByLabel), else one of its family (role; text, alt text and title; label and placeholder; test id; CSS). Otherwise it escalates to the most stable alternative, and when even that scores under 50 among alternatives from a snapshot, advises adding a data-testid. A replacement you picked by hand, Your pick, outranks them all. When the stored accessible name is provably gone from the failing page, name-based alternatives, the failing locator included, stay listed but are never recommended.

When a strict-mode violation matched several elements and only one is visible, the panel also suggests adding Playwright's .visible() (1.63 and later), the right fix when the duplicates are hidden copies rather than a naming problem.

Where it is ​

The Locator fix section of More ways to fix, on the execution and failure cluster pages; a cluster whose next step replaces the locator shows it under the situation block. The same result goes into the AI diagnosis context and the fix plan, and reaches agents through the get_locator_healing MCP tool.

Use it ​

Copy the recommended fix, or another alternative, and change the line the panel names. Two pickers in the panel let you click the element you meant instead: Pick from snapshot, when the failing locator is known, opens the failure-time DOM snapshot; Pick from trace, with an uploaded trace, opens the failure in the dashboard's trace viewer, whose Pick locator tool works on the recorded page snapshots. So a CI failure nobody watched can still be picked visually. A replacement you confirmed with one of them, or with the failure-time picker below, shows a Your pick badge and becomes the recommended fix.

The first later run whose code at that call site uses the recommended locator shows as healed in run #N, whoever made the edit.

Inspect the failing page live (local runs) ​

With inspectOnFailure: true (or PIWI_INSPECT_ON_FAIL=true), a failing test opens Piwi's own inspector overlay on its still-open page right before the browser closes. Click any element to get ranked, uniqueness-checked locators for it; one you confirm is recorded like a pick. It is not Playwright's inspector, so what you confirm flows back into the healing data when the failure names a locator to replace.

bash
# Linux / macOS
PIWI_INSPECT_ON_FAIL=true npx playwright test --headed

# Windows (PowerShell)
$env:PIWI_INSPECT_ON_FAIL='true'; npx playwright test --headed

Both local options need a headed browser (--headed or headless: false), never activate under CI (a CI provider's variable such as GITHUB_ACTIONS or JENKINS_URL, or CI set to anything but false or 0), skip expected failures (test.fail()), and with retries configured open only on the final attempt. The run waits while the overlay is open (the test timeout is lifted), so prefer --workers=1.

Pick a replacement locator on the failing page (local runs) ​

With pickLocatorOnFailure: true (or PIWI_PICK_LOCATOR_ON_FAIL=true), a test that failed on a locator, in an action (.click(), .fill()) or an assertion (expect(locator).toBeVisible()), gets the same overlay aimed at the locator that broke. Its steps are those of Piwi Picker's Pick an element: pick the element, choose stable parents to scope it to (optional, offered only for an element with a role), then Confirm one of the candidates. Unlike Pick an element, it ranks them by stability score without running each against the page or narrowing one that finds several elements.

bash
# Linux / macOS
PIWI_PICK_LOCATOR_ON_FAIL=true npx playwright test --headed

# Windows (PowerShell)
$env:PIWI_PICK_LOCATOR_ON_FAIL='true'; npx playwright test --headed

The pick is recorded in the run's locator snapshots, so the Locator fix panel shows it first once the run uploads, as a piwi-user-pick attachment and annotation in the Playwright report, and in the terminal with the call site and the replacement. The failure-time picker blocks the page's own click handlers while active, so picking can't navigate away.

Pause at a breakpoint (local runs) ​

With PIWI_PAUSE_AT=tests/login.spec.ts:42 (semicolon-separated file:line, relative to the working directory or absolute: tests/login.spec.ts:42;tests/pages/checkout.page.ts:9; an entry without a line is skipped, and the output says so), a call on a listed line that acts on, reads or checks the page (a navigation, an action, an assertion) waits before it runs, with a bar at the top of the page: Resume, Step (pause at the next call), Pick a locator (the picker above) and Finish (no more pauses); Esc resumes, unless the page takes it to close a dialog or an open list. A pick is recorded and printed like the failure-time one, and posted to PIWI_EDITOR_SEND, an editor's pairing address, with its line. Headed and never under CI, like the options above. The editor extensions set both from your breakpoints.

Limits ​

  • Healing runs only when the locator never resolved, matched nothing, or matched several elements. When it resolved and the step failed afterwards (element is not enabled, a wrong count, a hidden element) or the page failed to load, the panel says The locator resolved; this is not a locator problem (for a page that failed to load, The page failed to navigate before any locator ran), because a locator that found its element needs no rewrite.
  • Every suggestion but the diff rename needs a passing run captured with the fixtures; until then, without a diff rename, only the ARIA fallback applies. The diff rename reads the run's diff and the failing error, no snapshot. An Enter that submits at once can leave its field unread.
  • Capture reads each call site once per test, rarely twice. Negated assertions, absence checks (toBeHidden, toBeDetached) and multi-element checks (toHaveCount) are never probed. Turn it off with captureLocators: false or PIWI_CAPTURE_LOCATORS=false; it is also off whenever collectPerformanceMetrics is false.
