Issue tracking (Jira) ​

NeedsReporterAdministrator

An investigation ends with what a ticket needs: a headline, the affected tests and owners, the diagnosis, a validated patch, the verify command. Create issue makes it a Jira issue, linked back as the cluster's known issue.

It is off until an administrator connects Jira.

What it does, exactly ​

  • Create issue appears on a failure cluster, on a failing execution, on each inbox row (plus the c key and the inbox bulk bar's Create issues), and on a bug report. The cluster's Issue line and an execution's Cluster line offer Create issue and Link an issue until the cluster has a ticket, then name it, its summary on hover.
  • Link an issue pins an existing ticket: one on the site of the bound connection shows its live status; any other stays a plain link.
  • The issue body is the fix plan, rendered to Atlassian Document Format: What happened, Most likely, Evidence, What to do (patch, locator replacement, verify command, reproduce steps), Related issues fixed before and Links back to Piwi. Every section degrades independently.
  • Each issue carries the labels piwi, piwi-cluster-<id> and piwi-fp-<hash> and a Piwi-Cluster: <id> trailer for JQL.
  • Filing is deduped by cluster — a second click, a duplicate event, a rule or another of its executions names the issue already filed; once that link is removed or the issue is Done, the next create files a new one, and a Done issue stays linked. Before creating, the modal surfaces any issue that already tracks the failure (a pinned link, a matching label, or a fixed-before match) and leads with link it instead.
  • Creating an issue is a durable outbox action: attempted immediately, retried with backoff if Jira is down (the cluster and execution pages show Filing queued, with a retry), and recorded: the cluster's Activity lists each write Piwi makes to the issue. A create Jira refuses outright (a missing or invalid field) fails at once, with Jira's reason atop the modal and on the Issue or Cluster line; creating again replaces it.
  • Comment places your words first in the issue, or adds them to the cluster's issue already filed. Runs and tests: Issues about a run or a test.

The key travels ​

A cluster's known issue is its ticket filed or pinned, else one its tests name, open ones first; others stay among its links, which an execution's Details also lists. Its key follows the failure everywhere:

  • the cluster's Issue line and a failing execution's Cluster line, the inbox row and the execution's row in the run's test list show the key with its status; the search (Ctrl K) finds the cluster from the key;
  • cluster.new, cluster.fixed and cluster.regressed Slack messages name it, as does the cluster.new email;
  • the pull-request feedback comment says tracked in PROJ-123 on each failure whose cluster has one;
  • the fix plan lists it under Links, and the get_cluster / get_fix_plan MCP tools return it.

Links the tests declare ​

A failing test's piwi:issue or issue-key tag links its cluster to issues of the bound project. It counts as tracked, yet Piwi never writes to it and its status never resolves or reopens the cluster itself.

Keep the ticket honest ​

A background sync (PIWI_INTEGRATIONS_SYNC_MINUTES, default 15 min) reads each tracked issue back and caches its status, title and assignee (open clusters every sweep, resolved ones daily). Per-project policies, all off by default, each a durable deduped outbox action, write back as the cluster evolves:

When Piwi observesWhat Piwi does
A cluster's fix lands (stopped failing or diagnosis verified)Comments Fix landed in run #N …, and with transition on fix moves the issue.
A cluster regressesComments Regressed in run #N …, and optionally reopens the issue.
New occurrences on an open ticketAt most one note a day or a week: Still failing — +N occurrences in 3 runs …, with what is new.
A cluster is mergedWith comment on merge, notes it on both issues; the survivor inherits the links.
The ticket moves to DoneWith resolve on close, resolves the cluster unless its fix regressed. Otherwise, once the latest finished run no longer fails and the fix did not regress, the next step is Mark the cluster resolved — PROJ-123 is Done; while it fails, the Issue or Cluster line offers File a new issue.
The ticket is reopenedWith reopen on ticket reopen, reopens a resolved cluster with a note.

Both status policies act on a move of the ticket, so a person's reopen or resolve stands.

Every comment is written in the ticket's language; Issue automation adds diagnosis comments, description updates and the runs that write. An optional inbound webhook shows a close or reopen at once. The failure inbox gains a Needs ticket queue.

The project binding ​

A Project admin or an administrator binds the project under Project → Settings → Issue tracker: the connection, Jira project and issue type, default labels and assignee, the ticket language, what a ticket carries, the policies above, and owner routes — mapping a cluster's owner (@acme/checkout, an email) to a Jira project, component, assignee and labels. The create-issue draft picks the first matching route.

Tickets linked through a connection the project is no longer bound to keep their last status; the sync and the policies skip them.

Title prefix and who filed it ​

A title prefix such as [Piwi] starts every summary Piwi files. Set it on the project binding or as the connection's default; the binding's wins. It is up to 40 characters and counts toward Jira's 255, so a long title is cut, never the prefix. A title you type is filed as typed; one an agent gives through MCP gets the prefix. A summary edited in Jira never gets it back.

A ticket ends with Filed by Priya Shah from Piwi, naming the person once, as the cluster's Issue line does.

Required Jira fields ​

Piwi reads the issue type's create screen and asks for every required field it does not fill, such as a Severity or a Team:

  • The project binding's Jira fields block lists them; a value there fills every issue from the project.
  • The create modal shows them under Required by Jira, prefilled from those defaults, and keeps Create disabled until each has a value or a Jira default. A search in both adds any other field, custom ones included. An issue field, such as the Parent, searches Jira; a team is typed as its id.
  • The create_issue MCP tool refuses early, naming each missing field, its id and what it takes; an agent passes them in fields.

Transitions are checked the same way, as Issue automation explains.

Requirements ​

  • A connected Jira Cloud site — see Operate → Integrations.
  • A project binding naming the connection: a project's issues are filed, read and written back through that one connection, never through another.
  • PIWI_SITE_URL set, so the issue body's links resolve back to the dashboard.
  • The Contributor role or above to create or link an issue; anyone who reads the project sees the key and status.

Enable it ​

The modal files through the connection of the project binding and prefills its fields from the binding, else offers pickers over the bound site; toggles choose what the body carries (diagnosis and patch on, share link off). A share link needs the Maintainer role and is created when the issue is filed. From an AI agent, the create_issue MCP tool files the same ticket once the binding names a Jira project and issue type.

Language ​

A ticket's language follows its destination: the project binding's language, else the connection's default, else English. The create modal has a Language select; the create_issue MCP tool takes a locale. English and French ship.

Only the copy Piwi authors is translated: headings, fact labels, policy comments, dates and counts. Your data (test titles, errors, locators, paths, commands, the patch) is never translated. The model's prose follows the separate AI response-language setting.

Limits ​

  • Jira Cloud only (REST v3, email + API token).
  • A ticket's body is a snapshot at creation, unless description updates are on for an issue Piwi filed.
  • The dashboard's deterministic sentences (headline, story, clue, state line) are English templates, even in a French ticket.
  • Attachments honor the export size budget; the trace is never attached.

Try it in the demo ​

  • API Integration › POST /auth/login returns 200 with valid credentials: The login 500 is tracked in DEMO-42, filed from Piwi and In Progress in Jira; its key follows the failure to its executions and the inbox.
  • E2E Checkout › should complete checkout with Apple Pay: Its test names three DEMO issues with piwi:issue: DEMO-57 and DEMO-61 are linked from the test’s annotation, DEMO-64 is not in Jira, and DEMO-61 is Done, so the known issue is DEMO-57.
  • E2E Checkout › should complete checkout with PayPal: Its tag DEMO-52 names a Bug, linked with the chip From the tag; the credit card test’s tag DEMO-53 names a Task, which the binding’s issue type leaves out, so it is neither linked nor counted.
