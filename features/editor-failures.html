Failures in the editor ​

NeedsEditor extension

The editor extensions show the failures of the latest CI run at the lines that failed, lay your local runs over them, and follow each failing line through your edits until a run covers its test again.

CI failures in the Problems panel ​

The failures of the latest complete CI run on the checked-out branch, else the default branch, are in the Problems panel, at the line that failed: the call in the error's stack when that file is in your workspace (often a page object), else the test(…) line, with the failure's headline. In the spec, the line a failing test failed at is tinted darker, with ✗ Failed here, the reason unless a Piwi problem says it, Run this test, Screenshot and Trace above it.

On a failure, the light bulb lists Piwi's quick fixes, each titled Piwi: and its words. They edit the code but for the desktop app's jobs and File an issue; running the test, its trace, the context for an agent and its page in the dashboard are on the failure's node in the failures view, and running it and its trace above the line a spec failed at:

  • heal with … makes the edit an auto-heal pull request would, when locator healing has a recommendation for the failing locator.
  • run this test comes first once you rewrote the line it failed at, to check the edit.
  • reproduce in the desktop app, find the breaking commit in the desktop app and run Flake Lab on its untested suspects in the desktop app, for a test with an untested flake suspect, while the desktop app runs; share on … records the result.
  • apply the fix plan, then run its verification, when the failure's cluster has a fix plan whose patch applies to your files: the edit is previewed, then the plan's verify command runs in a terminal.

Hover for the error message, its call chain, the failure screenshot, and the tickets linked to its cluster or test. Without one, File an issue opens the cluster in the dashboard.

A failure of a run on the checked-out branch is an error; one from another branch, such as the default branch's while yours has no run yet, is a warning; one whose line you changed since the run is an information (a weak warning in a JetBrains IDE). The piwi.failureSeverity setting (Settings → Tools → Piwi → In the editor in a JetBrains IDE) chooses warning or information in place of the error, or off: nothing in the Problems panel, while the failures view, the gutter and the lines above the tests (unless piwi.codeLens hides them) still show the failures.

Your local runs ​

A later finished run on the branch, from the editor, piwi run, npx playwright test or the desktop app, overlays the latest CI run per test and Playwright project: a test it fixed leaves the Problems panel, its lens saying fixed locally in run #124; a test failing in it is an error that starts Local failure: and names local run #124, or your run #124 when this editor started it. The editor reads a run within a second of its end: After a run.

Failures follow your edits ​

A run reports the line a test failed at in the files it ran. The editor reads those files as the run saw them and follows each failing line through your changes, saved or not:

  • Add or remove lines above a failing line, and its error moves with it, in the Problems panel, the lines above the test and the failures view.
  • Rewrite the failing line, and the error turns into an information marker, Edited since run #120: …: the run said nothing about the new line. The reason above the line reads ✎ edited since run #120. The test keeps its failing mark until a run says otherwise.
  • Delete the test, and its failure leaves the editor.

The next run that covers the test says what is true: a failure there is an error again, and a pass takes it away.

For a CI run, the files as the run saw them are those of its commit (git show); for a local run, a run without a commit, or a commit your clone lacks, the files as saved when the editor first showed the failure.

The failures view ​

The latest run's failures as a tree: the Failures view of the Piwi panel in VS Code, the Piwi tool window in a JetBrains IDE. Its first node is the run, Run #120 · CI · feature/x · 3 failing · 1 fixed locally, with its age, or the progress of your run, running 4 of 9. Under it:

  • Your runs since lists the runs laid over it, such as #124 · your run · 2 min ago · 1 passed, 0 failed; a click opens one in the dashboard.
  • The failures, grouped by spec (the default), by failure cluster, by owner, or flat: Group the failures by…, in the view's title bar or the tool window's toolbar. The choice is kept for the workspace, and each group counts its failures.
  • A failure shows its title, where it failed (tests/login.spec.ts:42 · chromium · new), and an icon for failing, edited since the run, or fixed locally, with its run (your run #124, edited since run #120), its headline in the hover.
  • Flaky in this run: tests that passed on a retry, with Flake Lab's rate (flaky 18%). A test's menu offers its Flakiness tab and Flake Lab's commands (Look into this flake… in VS Code); the status bar's Show the run's flaky tests opens the group.

In a workspace with several Playwright configs, each config with a run, your runs or failures has a node of its own, named by its folder (apps/admin), with its project and counts beside it (Admin · 2 failing), over its tree as above. Its row in VS Code, and its context menu in both editors, re-run that config's failing tests (Re-run the failing tests) and open its run in the dashboard; the context menu adds Compare with… for that config. With one config, the run is the first node.

Click a failure (double-click, Enter or Next Occurrence in a JetBrains IDE) to open its line. Run this test, Open the trace and Open in dashboard sit on its row in VS Code; the context menu adds Go to the test, Debug this failure, Verify the test ×3, Open the screenshot, Copy context for agent, and, on a CI failure while the desktop app runs, Reproduce in the desktop app and Find the breaking commit in the desktop app. Heal stays a quick fix on the line.

The title bar, or the toolbar, holds Refresh the latest run, Re-run the failing tests (every config's), Open the latest run (the run the status bar shows; Open in dashboard in a JetBrains IDE, the page of the selected failure or run), Compare with… (for the active file's config) and the grouping. In VS Code, Follow the active editor, in the … menu, selects the first failure of the file you switch to until Stop following the active editor, and the badge counts the failing tests, as the tool window's title and its icon's red dot do. The JetBrains tool window's gear menu keeps Connect, Piwi Picker's pairing, the MCP configurations, Read the instance and the configs again, the settings and Open the documentation. The tree is read again when a run ends or an edit moves a failure.

With no failure to list, the view says why, in both editors: no failure in the run read; no run yet, or none for the baseline chosen, with Compare with…; an instance that does not answer, naming it and why, with Retry (also retried on its own); a desktop app to restart or update; an instance still being read; or no connection, with Connect. Re-run the failing tests stays while failures are listed, the instance answering or not.
