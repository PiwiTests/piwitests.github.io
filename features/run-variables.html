Run variables ​

Run variables are a few environment variables, NAME=value, that a project sets on every run Piwi starts for its tests and at the start of every command it gives to copy. They are for one app that serves several projects from one folder: each tenant is a project of the instance, and its tests need TENANT=acme to build, start and test the right one.

Set them ​

A project admin sets them in Project → Settings → Run variables: up to 10 rows of a name and a value, checked as you type.

  • A name is capital letters, digits and _, not starting with a digit, 64 characters at most, each name once.
  • A value is 1 to 500 letters, digits, spaces and _ - . , : / @ + =: a tenant, a region, a brand or an address (https://acme.example.com:8443/app). No $, backslash, quote or shell operator, no space at either end, and not starting with //.
  • Never a secret. Every copied command and every confirmation shows the values. A secret stays in each machine's own .env.
  • Refused names: a run variable never sets a variable that changes which code runs, which browser starts, which certificates are trusted, where results and requests go, or the CI a run reports. PATH, HOME, PREFIX, NODE_OPTIONS, BASH_ENV, HTTPS_PROXY, CI and COMSPEC are refused, and so is every name starting with PIWI_, PLAYWRIGHT_, NODE_, NPM_, GIT_, GITHUB_, LD_ or DYLD_, among others. Windows reads names whatever their case, so Path is PATH.

The settings save refuses a list with one refused variable whole, and each app that runs the tests checks the list again before it runs anything: a variable refused there runs nothing, rather than run without it.

Where they apply ​

  • Copied commands: the retry commands of a run, a test and a selection, Copy as command in the desktop app, the verify command of a fix plan, a saved selection's commands, the Flake Lab commands, and the test step of the reproduce recipe and its bisect. In bash a command starts with the variables (TENANT=acme npx playwright test …); in PowerShell it sets them for the rest of the session first ($env:TENANT='acme'; npx playwright test …). A copy button copies the form of the shell you last picked in a command block, else your computer's. The Markdown of a fix plan, an issue and an auto-heal pull request show the bash form.
  • The desktop app's runs: Re-run, Run with options…, Reproduce, Bisect, Flake Lab and a bug report's reproduction. The app reads the variables of its own project when it starts each run, never from the page, and the run's line in Local runs shows them. The install step of a checkout gets none.
  • Run on my machine: the confirmation lists them among its checks and starts the command with them. Run reads them again: when one changed since the window showed the command, it shows the new command instead of running. An app too old to apply them cannot take the request, which waits for one that can and says to update the app.
  • The editors' runs: VS Code and JetBrains run a test, a file, a selection, a debug run and the runs an agent starts with the variables of the project their folder follows. The first run asks you, Allow or Not now, once per set of values while the editor runs; until you allow them, Piwi runs nothing for the project. A run you start in a terminal is yours: Piwi sets nothing there.

A re-run in CI passes arguments only: a CI action picks its tenant with its fixed inputs, per deployment environment.

Per environment ​

Each environment of the project (Local, Staging, Production) holds up to 10 run variables of its own, with the same rules. A run Piwi starts for one gets the project's, then the environment's, the environment's value winning for a name both set, at most 20 together, and PIWI_ENVIRONMENT set to its key. The runs above and most copied commands offer the environment to pick (where); None, a fix plan's verify command and the reproduce recipe apply the project's alone.

Building and starting the app ​

Piwi runs no command of a project's settings before a run. Building and starting the app for a tenant belong in the Playwright config, so CI, a terminal, the editors and every Piwi run take the same steps, reviewed with the code:

ts
const tenant = process.env.TENANT ?? 'acme';
const port = { acme: 3001, globex: 3002 }[tenant] ?? 3000;

export default wrapConfig(
  defineConfig({
    use: { baseURL: `http://localhost:${port}` },
    webServer: {
      command: 'npm run build && npm start',
      env: { TENANT: tenant, PORT: String(port) },
      url: `http://localhost:${port}`,
      reuseExistingServer: !process.env.CI,
    },
  }),
  { projectName: `shop-${tenant}` },
);

A port for each tenant keeps reuseExistingServer from reusing a server another tenant started. The project name the config computes sends each run to its tenant's project.

One folder, several projects ​

The desktop app links one folder to as many projects as you like. Local folder in a project's settings names the other projects linked to its folder, and says when the config computes its project name rather than writing it out. An editor follows one project per folder: the one with the lowest id.

Limits ​

  • The PowerShell form keeps the variables set in that window: a command copied later for another project, in the same window, runs with them too. Copied commands are written for bash, zsh and PowerShell.
  • The commands the MCP tools return name no variable. The fix plan lists the project's run variables beside its verify command, and tells an agent to set them.
  • Listing the tests of a config for the editors' test tree sets no variable.
