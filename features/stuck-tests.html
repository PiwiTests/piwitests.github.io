Stuck tests ​

NeedsReporter

A CI run that never ends is often one test waiting on something that will not come: a button that stays disabled, a page that never loads, a lock never released. Piwi says so while the run is still going. A running test that has run far longer than it usually does is marked Stuck? on its run page, and a test.stuck notification goes to the project's channels. Nobody needs to have the run open, and the live view does not need to be on.

When a test is stuck ​

The dashboard checks the running tests of its live runs every 15 seconds. A test is stuck when its current attempt has run longer than both:

  • two minutes, whatever the test usually takes;
  • three times its longest duration among its last ten passing executions on the same browser.

A test needs two passing executions on that browser before any attempt of it can be stuck: a new test is never flagged. The executions read are the ones a baseline reads, so no Flake Lab or investigation run and no environment incident. The time counts from the start the attempt's begin event names, else from when the dashboard heard it begin; the reporter's begin events name none. Each attempt is said to be stuck once; a retry is a new attempt.

A test of a run on a developer's machine may stand stopped at a breakpoint or a page.pause(). With @piwitests/reporter 0.68.0 or later its run tells the dashboard so: the test is never said to be stuck while it stands stopped, and the time it stood stopped is left out of how long it ran.

The question mark is meant: a test can be slow for a good reason, a large import or a cold cache. The rule says only that this attempt is far outside what its passing runs took.

On the run page ​

A stuck test's row on the run page's Tests tab carries a Stuck? badge, how long it has run and the longest its last passing runs took: Running for 7 minutes, usually 41.2s at most. The row's live step names the step it is in. With the project's live view on, Watch shows its page and, in a CI run, what its current call waits for. The badge leaves the row when the attempt ends. A test that stands stopped says where in its place: Stopped at a breakpoint · Click getByRole('button') · tests/checkout.spec.ts:18 · for 3 minutes.

A page opened after the test was said to be stuck shows it too: the dashboard keeps it with the running test.

On the Timeline ​

While a run runs, its Timeline tab shows each worker's lane, grouped by shard, with a bar for every attempt. A running attempt's bar grows to now over a pale bar of its test's usual time: the longest of the last passing runs this rule reads. Once it runs past that time, a white tick marks where it would usually have ended, and it turns amber once the test is marked Stuck?. A test with too few passing runs has no pale bar. The header counts the stuck tests, and a sharded run's says which of its shards have started: shards 1 and 3 of 4 started.

On the Tests tab, is:stuck lists the stuck tests, and worker: and shard: narrow the list to one worker or one shard (Test search).

The notification ​

test.stuck fires once per attempt, through the channels of the project's subscriptions that chose it. Its message names the test, how long it has run against its usual time, the run with its branch and environment, the browser and worker, and the test's owner. Its button opens the run with its Tests tab searched for the test, and the live view of its worker where the project has it on. The payload is on Notification events & webhooks.

The branch, environment, owner and Default branch only filters apply to it. A run started on a developer's machine sends none, complete or not: a run from a terminal, the desktop app, an editor, piwi preflight --run or piwi bug --write is marked Stuck? on its run page and notifies nobody, since its test may be stopped at a breakpoint. A bisect step or a reproduction sends none either. A CI job the reporter does not detect as CI records its runs as local: set PIWI_ORIGIN=ci on it (run origin).

Limits ​

  • A live run on this dashboard. The running tests are kept in the memory of the server the run reports to, as the run's live events are. A dashboard that restarts forgets them until each test's next attempt begins, and it needs one dashboard server (Resource requirements).
  • Fixed thresholds. Two minutes and three times the longest pass are the same for every project.
  • No history, no verdict. A test with fewer than two passing executions on its browser is never said to be stuck.

Try it in the demo ​

In the live demo, pick Stuck test in Simulate a test run: the PayPal checkout waits on a payment that never answers, and its row carries the Stuck? badge once it runs past its usual time; on the Timeline tab its bar turns amber past the pale bar of that time. Stopped at a breakpoint plays a run from VS Code whose PayPal test stands at a breakpoint for five minutes: its row says where, and never reads Stuck?.
