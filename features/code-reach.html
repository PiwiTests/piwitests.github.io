Code reach ​

Code reach answers "which tests reach this file?" for application code: an opt-in capture records the source files whose functions ran during each test in the browser, so a change to a component or a module maps to the tests that execute it. An ASP.NET Core backend built for coverage adds the code each test ran on the server: server coverage.

Turn it on ​

Set captureCodeReach: true in the reporter options, or PIWI_CAPTURE_CODE_REACH=true, with the capture fixtures in place. Coverage adds time to every test and reach changes slowly, so turn it on in one scheduled job; a run without it keeps the reach the last one recorded.

ts
// playwright.config.ts, in the nightly job
reporter: [['@piwitests/reporter', { captureCodeReach: !!process.env.NIGHTLY }]],

What it records ​

The fixtures start Chromium's JavaScript coverage on each page the test opens, and on up to 16 pages already open as it starts (a beforeAll's, an earlier test's), and at teardown turn each script into source files:

  • a module a dev server serves by path (Vite's /src/components/Pay.vue, /@fs/…) is the file itself;
  • a bundle is read through its source map, inline or fetched once per worker (20 MB and 5 seconds at most).

A file counts when one of its functions ran. A module's top-level code runs as soon as it is imported, so it does not count, or every eagerly loaded file would be reached by every test. Paths are relative to the repository root; files under node_modules or outside the repository are dropped, and at most 2,000 files are kept per test. Only the paths leave the machine, never code, counts or line numbers.

coverage.browser: 'files' is the same as captureCodeReach: true; 'functions' adds each function's start and end line, through the source map, and the file's git blob: line numbers then leave the machine. With 'functions', the run also records every function the pages' scripts declare, run or not, so the run's coverage can say how many of a file's functions ran. A function declared inside a function that never ran is not listed: V8 has not seen it.

Paths resolve against the Playwright config's directory, then the repository root. Set codeReachRoots to the dev server's root when it is elsewhere; for Nuxt that is app/:

ts
reporter: [['@piwitests/reporter', { captureCodeReach: true, codeReachRoots: ['app'] }]],

When the tests reach several dev servers that serve modules at the same paths (one per portal, each with its own /js/index.ts), give codeReachRoots an object: each origin with its directories, * for every other origin. A script resolves against its own origin's directories, else those of the page that loaded it, so the key can be the address the tests open:

ts
codeReachRoots: {
  'http://localhost:5001': 'portals/admin/src',
  'http://localhost:5002': 'portals/customer/src',
  '*': ['shared'],
},

Code a bundler or dev server adds (module wrappers, hot-reload hooks) counts for no file.

With an instrumented backend (the Nitro or ASP.NET Core packages), the handler file of each route a test called counts as reached too.

Supported builds ​

BuildSource maps
Vite dev server, Nuxt dev includednone needed: modules are served by path
Vite buildbuild: { sourcemap: true }

Next.js build, Turbopack or webpackproductionBrowserSourceMaps: true

The map must be linked from the bundle: sourcemap: 'hidden' and webpack's hidden-source-map write the map but not the comment that names it, so they record nothing.

Each was checked on a React app (Vite 8, webpack 5.111, Next.js 16.3) and Piwi's own Nuxt dev suite: every test recorded exactly the files it ran.

Cost ​

Code reach reads V8's function coverage, which records only whether each function ran. A test pays for a CDP session on each page it has, a debugger stop and a coverage read for each document it leaves, and a script's source is read once per worker, so the cost grows with the modules each document loads. One script-heavy page costs about 8% more per test; on a large ASP.NET Core and Vue application, served by Vite dev servers and moving between screens by full page loads, its UI tests took 40 to 50% longer, by file or by function alike: turn it on in a scheduled run there. Coverage cost has every mode and how each was measured.

On the execution page ​

An execution's Source tab lists what the test ran: server files by executed lines, then browser files. A file the failure's suspect lines name, or that changed since the last pass, is marked. A file with line numbers unfolds to its source at the version the test ran, marking what it ran and, from the run's own coverage, the executable lines it did not.

Which tests run a file ​

A file's tests link, on an execution, a cluster's suspect lines or the Test Map, opens its coverage page: its source at the version most tests ran, each line with how many tests ran it, the executable lines none runs marked. Select a line or a range for its tests and their latest outcome; on a line no test runs, the nearest test to copy.

Where it is used ​

  • Impact-from-diff maps a changed file to the tests that executed it, and with function or line coverage to the tests that ran the changed lines (line level); a changed file no test reached still widens the run to the whole suite, since code reach misses top-level code, server code without server coverage and type-only modules.
  • Uncovered changes counts a changed file as reached when a test executed it.
  • Locator preflight calls a break likely only when one of its tests reaches the changed file.
  • Coverage in the editor marks the lines tests ran and the ones none runs, in VS Code and the JetBrains IDEs.
  • Suspect lines: the changed lines a failure's tests executed, on the failure pages' What changed, in the AI diagnosis and the fix plan.

The API (/docs on your instance) serves the tests reaching a file and a branch's map.

Limits ​

  • Chromium only in the browser: other browsers have no JavaScript coverage and record no browser files. Server coverage works with every browser.
  • Browser files are reached, not covered: a reached file may hide an untested branch.
  • A build with neither per-module URLs nor source maps yields nothing, and so does code rendered on the server only, React server components included.
  • A module whose top-level code calls its own functions, a table built on import, counts for every test that loads it.
  • A function a minifier inlines into another counts for the file it was inlined into.
  • Chromium drops the coverage of a document the page leaves, so each document is read as it goes: the capture adds a beforeunload listener in an isolated world, out of the page's reach, and the debugger stops on it for that read. A document left without beforeunload (a crash) keeps only what an earlier read saw.
  • On a page open before the test, what ran there before counts only if it runs again, and what a page runs on its own meanwhile (a timer, a poll) counts too.
  • Reach is per branch: a branch's own runs replace its tests' reach, and the default branch's stands in for the rest.
