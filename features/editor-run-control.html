Pause and step from the editor ​

NeedsReporterCapture fixturesEditor extension

A test run the editor extensions start, or one started outside Piwi, can be paused, stepped and resumed from the editor with Piwi's own commands: no debug session starts, and the IDE's debugger works as usual beside it. The editor marks the line the test stopped at, and the breakpoints you set or remove reach the run while it goes on. The pause bar and Piwi Picker's Runs window answer the same stops; the code a stop writes is on Code from a pause.

The controls ​

ControlWhat it doesVS CodeJetBrains IDEs
PauseStops a running test before its next call that acts on, reads or checks the pagenonePause Program's
ResumeRuns the stopped test on to the next breakpointF5Resume Program's, F9
StepRuns the call and stops before the next one, breakpoint or notF10Step Over's, F8
Run to cursorStops at the first call on the cursor's line (on a statement broken over lines, at its call), or at a breakpoint before itCtrl+F10Run to Cursor's, Alt+F9
FinishRuns the test on without stopping at a breakpoint again in this attemptShift+F11Step Out's, Shift+F8
End the testSkips the rest of the test, and a stopped locator call from Playwright 1.62nonenone
StopEnds the run's processShift+F5Stop the run, or the Run tool window's Stop

The keys are the IDE's debugger keys (in a JetBrains IDE, your keymap's), Piwi's only while their control applies and the debugger does not take them. On macOS, Cmd+F10 runs to the cursor in VS Code. Pause and End the test have no key in VS Code: bind one in Preferences: Open Keyboard Shortcuts (search piwi). Within two seconds of an answer, until that worker stops, a key answers no other worker and starts no debug session.

  • In VS Code, the controls are in the Piwi item's menu while they apply, after Go to the stopped line, in the palette (Piwi: Pause the run and its kin) and the editor title (Resume, the rest under …).
  • In a JetBrains IDE, they are under Tools → Piwi, enabled while they apply, and in the status bar item's menu, whose text says why and where a test stopped.

The item's line comes from the run, so it counts offline and with the desktop app (Watch a run); its tooltip names the other tools that have the run open.

Pause stops every run Piwi started in this window (in a JetBrains IDE, this project), each worker before its next call that Playwright's debugger stops at (which calls): a long call or a waitForTimeout finishes first (End the test gives up a locator call at once), and a worker between tests stops at the next test's first call. A test that never stops, under CI or Playwright's debugger, says why.

Where the test stands ​

When a test stops, at a breakpoint, after Step or Pause, on the line it was run to, at page.pause(), or at a failure, the editor opens the file of the call about to run, with the cursor on its line, and marks it: an arrow in the gutter, the debugger's execution point color, and above it the call, as Playwright names it, with the controls:

Stopped at a breakpoint · Fill "MORNING10" getByLabel('Coupon code') · attempt 2 Resume Step Run to cursor Finish End test

It says why the test stopped; attempt 2 shows on a retry. VS Code's CodeLens holds Resume, Step, Finish and Write code…, its hover all controls; the color is piwi.executionPointBackground. In a JetBrains IDE the line is an inlay whose words are links, the arrow's click lists the controls, and the color is Settings → Editor → Color Scheme → Piwi → Line a run is stopped at. The mark goes when the test goes on (from the editor or the bar), ends, or closes its page.

With several workers stopped, each has its own mark. A stop takes the cursor only on the worker you last answered or worked on, or as the first shown while no step waits; another opens beside your editor, or, in a busy JetBrains IDE, waits in the status bar's menu. The controls above a line act on its worker, a key or command on the one at the cursor's line, else the only one shown, else it asks which. A control answers the stop it was shown for: when the test went on meanwhile, it says so and asks nothing.

The run's code is your files as they stood when it started. The mark follows lines you add or remove above it, and Run to cursor in an edited file runs to the run's line for the cursor's, or says a line written since has none.

A headless run ​

A run Piwi starts follows your config, headless by default, unless you choose Run headed or an older reporter needs it. A headless stop opens Piwi: paused page beside VS Code's editor, or Paused page in the JetBrains Piwi tool window, which keeps its stop until it goes on, and after a Step or Run to cursor from the editor waits up to 10 seconds for its next stop. Piwi: Show the paused page (Tools → Piwi → Show the paused page) opens it at any stop.

Clicking the image picks a locator when the reporter supports it, on Playwright 1.60 or later: it replaces the stopped line's, and the tab shows the result or refusal.

Watch updates the paused page until you hide or close the tab, resume or switch stops, and Interact plays your input on it, taking the stop. The preview uses the editor's connection: no Picker, pairing, live-view setting or port forwarding. Older reporters keep the still image. To watch the test before it stops: Watch a running test.

Share with Playwright tools ​

At a stop, Share with Playwright tools (the stop's hover and Piwi: Share the stopped test's browser with Playwright tools in VS Code; the stop's menu and Tools → Piwi in a JetBrains IDE) binds the test's browser for Playwright's own tools, so npx playwright cli attach piwi-<run>-w<worker> and Playwright's dashboard can join it. It is off until you ask, and asks first each time: any process of yours can then read the browser's pages and run code in them. It stays shared until the test ends; no agent can share it.

Breakpoints while the run goes on ​

A breakpoint you add, remove or toggle applies to the run from its next call, in every worker, later ones included. One that only moves because you edited the lines above it keeps the line the run has, and one you set in an edited file applies to that line of the run's code. The breakpoints that count are those a run's start reads: line breakpoints in script files under a Playwright config's folder, while piwi.breakpoints (Pause the runs Piwi starts at the editor's breakpoints in a JetBrains IDE) is on. A logpoint, or a breakpoint that does not suspend, never stops the test; a condition is not read, so a conditional breakpoint stops at each pass.

How it works ​

With a reporter newer than 0.59.0, each worker of a Piwi run stays connected to the editor service through a socket only you can read (PIWI_RUN_CHANNEL), saying which test it runs and where it stops. Closing the IDE closes the connections: a stop with no pause bar then goes on, one the bar shows waits there.

Limits ​

  • No mark on a breakpoint that never stops. One on a line with no call Playwright's debugger stops at looks like any other and does nothing.
  • Playwright calls, not JavaScript. Step goes from one Playwright call to the next; stepping through the test's code stays with the IDE's debugger.
  • No image when the page is unknown. A stop at a call other than a locator's (a navigation, a key press) in a browser context with several pages has no image, and refuses Piwi Picker's Pick and Record: the worker cannot tell its page. Any page of that context closing ends it.
