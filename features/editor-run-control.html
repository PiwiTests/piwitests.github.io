Pause and step from the editor ​

NeedsReporterCapture fixtures

A test run the editor extensions start can be paused, stepped and resumed from the editor, with Piwi's own commands: no debug session starts, and the IDE's debugger works as usual beside it. The editor marks the line the test stopped at, as a debugger does, and the breakpoints you set or remove reach the run while it goes on. The pause bar in the page answers the same stops, as does Piwi Picker's Runs window, with a shortcut you set to pause and resume from any window. At a stop, the editor also writes code from the page: Code from a pause.

The controls ​

The keys are the IDE's own debugger keys (in a JetBrains IDE, your keymap's, the default one's shown), Piwi's only while their control applies and no debug session runs. Where a JetBrains keymap also gives one to another action (the VSCode keymap's F5, NetBeans' F4), Piwi's goes first while it applies. On macOS, Cmd+F10 runs to the cursor in VS Code. Pause has no key in VS Code, since it applies as long as the test runs: bind one in Preferences: Open Keyboard Shortcuts (search piwi), where the others change too. There, F5 pressed again within two seconds of an answer waits for the next stop rather than start a debug session.

  • In VS Code, the controls sit in the status bar beside the run's progress: Pause and Stop while the test runs (Pausing… until it stops), Resume, Step, Finish and Stop while it is stopped. The palette has them while they apply: Piwi: Pause the run, Piwi: Resume the run, Piwi: Step to the next call, Piwi: Run to the cursor, Piwi: Finish the test without stopping again, Piwi: Stop the run and Piwi: Show the paused page.
  • In a JetBrains IDE, they are under Tools → Piwi, enabled while they apply, and first in the status bar item's menu, which reads Piwi: paused · checkout.page.ts:12 while a test is stopped.

Pause stops every run Piwi started in this window (in a JetBrains IDE, this project), each worker before its next call that Playwright's debugger stops at (which calls): a long call or a waitForTimeout finishes first, and a worker between tests stops at the next test's first call. A test that never stops, under CI or Playwright's own debugger, says why.

Where the test stands ​

When a test stops, at a breakpoint, after Step or Pause, on the line it was run to, at page.pause(), or at a failure, the editor opens the file of the call about to run, with the cursor on its line, and marks it: an arrow in the gutter, the debugger's execution point color, and above it the call, as Playwright names it, with the controls:

Paused · Fill "MORNING10" getByLabel('Coupon code') · attempt 2 Resume Step Run to cursor Finish

attempt 2 shows on a retry. In VS Code the line is a CodeLens, and the marked line's hover has the same controls; the color is piwi.executionPointBackground. In a JetBrains IDE the line is an inlay whose words are links, the arrow's click lists the controls, and the color is Settings → Editor → Color Scheme → Piwi → Line a run is stopped at. The mark goes when the test goes on (from the editor or the bar), ends, or closes its page.

With several workers stopped, each has its own mark, and the controls above a line act on its worker; a key or command acts on the one at the cursor's line, else asks which. A control answers the stop it was shown for: when the test went on meanwhile, it says so and asks nothing.

The run's code is your files as they stood when it started. The mark follows lines you add or remove above it, and Run to cursor in an edited file runs to the run's line for the cursor's; on a line written since, it says the test has none.

A headless run ​

A run Piwi starts with breakpoints is headed, so the pause bar answers its stops too. One started without runs as its config says, headless by default: when you pause it, or it reaches a breakpoint set since, no bar shows, and the editor shows an image of the page at the stop: in VS Code in a Piwi: paused page tab beside the editor, in a JetBrains IDE in the Piwi tool window's Paused Page tab. It is taken again at each such stop; Piwi: Show the paused page (Tools → Piwi → Show the Paused Page) asks for it at any stop.

Whoever answers it, a stop counts as one at the bar: the test's duration leaves it out, and the dashboard's timelines draw it as a Paused band, with why it stopped.

Breakpoints while the run goes on ​

A breakpoint you add, remove, enable or disable applies to the run from its next call, in each of its workers, those Playwright starts after a failure included. One that only moves because you edited the lines above it keeps the line the run has, and one you set in an edited file applies to that line of the run's code. The breakpoints that count are those a run's start reads: line breakpoints in script files under a Playwright config's folder, while piwi.breakpoints (Pause the runs Piwi starts at the editor's breakpoints in a JetBrains IDE) is on. Turning the setting off lets the run go on without them.

How it works ​

With a reporter newer than 0.59.0, each worker of a run Piwi starts stays connected to the editor service while it runs, through a socket the service opens on your machine, readable by you only, named in the run's environment as PIWI_RUN_CHANNEL. The worker says which test it runs and where it stops; the editor answers with the controls. A run whose connection does not open, or closes, pauses as it would without it. Stopping the editor service, or closing the IDE, closes the connections: a stop with no pause bar then goes on, and one the bar shows waits there for its answer.

Limits ​

  • Runs Piwi started only. A run started in a terminal, or by the IDE's own Playwright run configuration, has no controls in the editor; with Run the tests in the IDE's Playwright runner on, a JetBrains IDE's runs keep them, their Rerun, Rerun Failed Tests and Debug included.
  • No mark on a breakpoint that never stops. A breakpoint on a line with no Playwright call, or only calls Playwright's debugger never stops at, looks like any other and does nothing.
  • Playwright calls, not JavaScript. Step goes from one Playwright call to the next; stepping through the test's own code stays with the IDE's debugger.
  • One image a stop. The paused page is a still image: it does not follow what you do in a headed browser.
  • No image when the page is unknown. A stop at a call other than a locator's (a navigation, a key press) in a browser context with several pages has no image, and refuses Piwi Picker's Pick and Record: the worker cannot tell which page the call is on. Any page of that context closing ends it.
