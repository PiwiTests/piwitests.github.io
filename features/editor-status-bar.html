The editor's status bar ​

NeedsEditor extension

The Piwi item in the status bar of the editor extensions says how the latest run of your branch went, or how far a run in progress is, for the Playwright config of the file you are editing, with its tests that may be stuck (· 1 stuck?).

The latest complete run on the branch: how many tests passed, how many still fail (Piwi: 2 failing), or, with none failing, how many your local runs fixed (Piwi: 1 fixed locally); its tooltip counts what your local runs fixed and the flaky tests. A recording in progress takes the item, in both editors, its controls in the item's menu; a test that waits for you keeps it. While a run started from this editor, or another run of the branch, is in progress, the item says where its test stands stopped or the call a paused one waits in, that it is shared live, and how far it is (Piwi: held at its failure · checkout.page.ts:12 · run #124 · 4 of 9 · 1 failed), another's naming its branch (CI run #130 on feature-x) and, in the tooltip, where it comes from (from the desktop app, on a developer's machine), in the same words in both editors, and returns to the latest run when it ends. A test that waits for you marks the item until you answer it: its background turns yellow in VS Code, and its icon takes a dot in a JetBrains IDE. A run you started keeps the item whichever Playwright config the active file belongs to, and VS Code's Testing view shows a run that is not yours with its tests' results as they end, never as your tests running. The editor follows the two newest CI runs of the branch, through the connection to the instance it already holds, and while it follows one, the run's reporter streams the call each test is at.

With several Playwright configs, the item speaks for the config of the file you are editing, the deepest config folder that holds it, and follows you from file to file; outside every config folder, it shows the first connected config. Its tooltip names the config (The active file's Playwright config, in apps/admin (one of 3)), then holds the run's counts, the baseline, your local runs since, the run in progress, and when the run was read (Updated 12 s ago · live while the event stream is connected, · read every minute without it).

In VS Code, a click opens Piwi: Open the Piwi menu, in the JetBrains menu's sections, the item's own action first: Enter reads the latest run and its failures again (Refresh the latest run), without the indexes and configs Read the instance and the configs again reads, or goes to the stopped line while a test is stopped. The run's controls and its share are in the menu while a run is live. When the extension is not connected, the item says why, and its first entry is Connect…, or Read the instance and the configs again for an unreachable instance or a desktop app to restart.

The item turns red (its background in VS Code, its text in a JetBrains IDE) only for a test a run you started from the editor failed that the baseline does not fail, until a run fixes it or the editor restarts: a CI failure or a teammate's is counted, never red, and so is a run in progress. piwi.statusBarAlert in VS Code, and The status bar item's text turns red on Settings → Tools → Piwi in a JetBrains IDE, choose any failing test or never instead.

In a JetBrains IDE, an icon before the text shows the state of the run the item counts (running, failing, passed), of a recording, or of the connection. A click opens a menu of the Tools → Piwi actions that apply, led by what the item calls for: Refresh the latest run, Read the instance and the configs again for an unreachable instance or a desktop app to restart, Connect… while not connected, Node.js settings… when Node.js is missing or too old, or Go to the recorded lines while a recording runs, with Pause recording, Resume recording and Stop recording.

Compare with another run ​

By default, failures are read against the checked-out branch's latest complete run, else the default branch's. Piwi: Compare with… (Tools → Piwi → Compare with… in a JetBrains IDE, and the failures view's title bar) chooses another run to compare with: a branch's latest complete run, a run by its id, or My local runs only, your runs from this machine, without CI. Your runs since are laid over each. The status bar tooltip and the failures view name it (Baseline: CI run #120 on feature/x), ending with (no run) when it found none. That run need not have passed: it is not the dashboard's baseline, the last passing run. The choice is kept on this machine, per Playwright config.

A test that waits for you ​

A test held at its failure, or stopped at page.pause(), while the editor is in the background, calls you once: a notification with Resume and Go to the stopped line in VS Code, the system's attention request (a bouncing or flashing icon) in a JetBrains IDE, which also comes to the front while you are in another application and the debugger's Focus application on breakpoint is on, as it is by default. A stop you asked for, at a breakpoint, a Step or a Pause, never does, nor one an agent drives or a desktop app's job, which calls from its own window. A paused run has the controls, and Runs from the editor starts them.
