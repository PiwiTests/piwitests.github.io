Desktop app ​

NeedsDesktop app

The desktop app runs the entire dashboard on your machine, with no Docker, npx or server to set up. It bundles the Docker image's server in a native window and adds what only a local app can. Its runs: Local runs tray for each run, Desktop app runs for each worker.

What it does ​

  • Receives your local runs with no URL or token in your Playwright config.
  • Links a project to its folder, so a run page can re-run the failed tests here.
  • Reproduces and bisects a failure, or a flake, in a throwaway worktree, also for your editor.
  • Imports a blob report or trace dropped on the window.
  • Connects AI assistants to its MCP server by writing their config.

Everything binds to 127.0.0.1.

Where it is ​

Piwi Desktop

What each installer needs:

The installers, Piwi Runner's too, are unsigned: on macOS, open the app once, then Open Anyway in Privacy & Security; on Windows, More info then Run anyway in SmartScreen.

Its data, and how to back it up: the desktop app's data.

The tray menu, in the editors' order: Show the stopped test if one waits, Open Piwi Desktop, Stop per running test (machine kept awake), MCP server…, Desktop app settings…, Run in background (off, closing the window quits), Start on login, Check for updates…, Open data folder, Show logs, Quit Piwi Desktop. The windows open where you left them, with keyboard shortcuts and macOS menu items. Open in a window, on a worker of the Local runs tray, keeps that worker in a window above the others. While a run reports into the app, from the app, an editor, a terminal or CI, its progress shows on the taskbar button or the Dock icon and in the window's title (Running 3/9), and a dot on the system tray icon (and the taskbar button, on Windows) says how it stands: blue while it runs, red once a test failed, violet while a test of the app's runs, or of an editor's, waits at a stop for you (1 test waits for you). A run from the window's Local runs tray flashes its outcome as it ends (slate when interrupted), whatever else runs, and, failed while you look away, bounces the Dock icon or flashes the taskbar button, a bisect or a lab only at its verdict; an editor's, a terminal's or CI's run, or one from before a reload, never does. On Windows, the taskbar button's thumbnail has Open, which restores the window, and Stop, which stops the window's run started last, the next one at a second click. In the background, notifications arrive as OS notifications with no setup, plus an unread count on the dock icon or system tray tooltip.

It listens on port 3000, or the one set in the .exe installer or in Settings → Desktop app (serverPort in settings.json), a free one when taken.

Sending results to it ​

While the app runs, the reporter finds it itself: a config with only a projectName reports here. It reads the address and token the app writes to ~/.piwi/desktop.json only when nothing else sets a server, so a CI job is never redirected, and sends the token only to a server that proves it holds it (details). A suite reporting to a shared dashboard sends its local runs here with desktopApp: 'prefer', which the Connect a suite snippets carry with CI reports to a team server on.

When the tests run as another user or in a container, Settings → Desktop app gives the address and token to configure by hand. Keep the token in PIWI_API_KEY.

A dashboard link opened in your browser opens in the app, closing its tab. A piwi://open/<page> link opens its page there, starting the app if needed (macOS: from Applications; Linux: after one run).

Projects from local folders ​

A project's folder holds its Playwright config (a monorepo's subfolder, not its root). Projects → New project → Choose folder… creates a project from one, named as it would report, and checks its setup: npx @piwitests/reporter init there fixes what is missing. The link stays local, under Project → Settings → Local folder, with its checks, Unlink and Change, which suggests folders and checks your pick. Linking it offers to import its earlier runs; Open in editor resolves source links against it when no workspace root is set; and a clone serves its git history without an SCM credential.

Running tests from the app ​

A run, an execution, a cluster or a test runs again here with the folder's own Playwright, and its button says what: Re-run 3 failed tests, Re-run this test, or Run this test (×20 until a failure, traced) on a test case.

  • The arrow shows the command, runs it once headed, in the inspector or UI mode, and sets its options: tests by file:line, title or file, a trace, --repeat-each without retries (up to 1,000 in Run with options…), stopping at the first failing repetition, and Hold failures. The button names what differs from Playwright's defaults (· headed · ×5); set the project's in Project → Settings → Local folder.
  • On a run, the arrow also re-runs its flaky tests or all of them, and the Tests tab a selection.
  • Runs keep going while you browse, in the Local runs tray, each under what it runs; results come here, with Compare with run #N. A bug report from Piwi Picker runs there too.
  • Wrong folder? With none of the tests in it, the button opens the link's dialog.
  • Watch, pause and step each worker from the Local runs tray, running or stopped: Desktop app runs. While it goes on, the run's own page shows the same (On your machine), with its Stop, Hold failures and output.

Reproducing a failure and finding the breaking commit ​

A fix plan's reproduce and bisect recipe can run here, against the linked folder, without touching your checkout:

  • Reproduce here checks out the failing commit in a throwaway git worktree, installs its dependencies (reusing yours on an unchanged lockfile outside a workspace) and any missing browser, and runs the failing test with that commit's own Playwright, stopping in your editor when one is open.
  • Find the breaking commit here bisects between the last green commit and the failing one, with live progress and a Stop that kills the test and what it started, resets the bisect and removes the worktree. The first bad commit is linked to your SCM host and recorded on the failure cluster.

Jobs from your editor ​

On a team instance's failure, the editor extensions offer Reproduce in the desktop app and Find the breaking commit in the desktop app; on a flaky test, or a failure whose test has an untested suspect, a Flake Lab run of the team instance's plan. The window shows the commits, tests or arms and runs nothing until you start it. The editor gets the verdict and can share it on the team instance with its own key, which the app never holds.

Importing local files ​

Drop a Playwright blob report or trace (.zip) on the window, or open one with Open with → Piwi Desktop, and pick the project: it imports as on the import page, several traces forming one run. A .piwibug becomes a bug report.

Connecting AI assistants ​

The app serves the MCP server with local tools a hosted instance lacks: import_local_report (a local .zip into a project), read_local_source (the file on disk now), apply_locator_fix (a recommended locator fix applied to the file, previewed by default), and the run tools for the runs it starts. It registers as piwi-desktop, beside a hosted Piwi.

Settings → MCP server connects Claude Code, Cursor and other clients it detects in one click: the desktop app's client setup.

Updates ​

Settings → About → Updates checks for a newer release (also at startup), lists what changed since your version, breaking changes first, and installs it on restart; the tray's Check for updates… installs and restarts. The .exe needs no admin rights; the .msi does. Downloads are signature-checked.

Limits ​

  • One machine, one user. It accepts results only from this machine; a team needs the Docker image.
  • Local runs need the checkout: a linked folder with Playwright installed, plus git and your package manager for reproduce, bisect (one repository) and the lab.
  • No public address: no pull-request feedback, auto-heal, share links or Jira webhook; email only with SMTP set.
