Desktop app runs ​

NeedsCapture fixturesDesktop app

Every Playwright run the desktop app starts names the app as its hub: Run locally, a reproduction, a bisect step, a Flake Lab run and a bug report's run. Its Local runs tray shows each worker of the run beside its output, and steers the test as the editor does: Pause and step from the editor. Nothing leaves your machine unless you share a run live.

Each worker ​

While a run goes on, the tray shows each worker's test, its Playwright project and its attempt, and whether it runs. Pause stops the test before its next call that acts on or checks the page. A test also stops at a page.pause(), and a headed one shows Piwi's pause bar there.

At a stop, the tray says why the test stopped, the call about to run and its place in your code, with an image of the page. Resume lets the test go on, Step runs one call and stops before the next, Finish runs the test to its end without stopping again, and End the test skips the rest of it.

Hold failures, on each running run in the tray, holds a failing test at its line: Failed at, its error under it, and Resume to let it end as it failed. It is off for a run you start, and on from the start for Reproduce, which runs to show you the failure; while Piwi Picker's Runs window is open, failures are held too. A run nobody attends never holds one, and its switch says so: a Flake Lab run, a bisect, a lab job, a run with --repeat-each above 1 and UI mode go on past each failure.

The tray opens at each stop: a headless test waits for you there. While the window is in the background, the system tells you of a failure or a page.pause(), never of a step or a pause you asked for. When no run of the app is going on, the window stops listening, and a stop goes on at once.

Watch live ​

Watch live shows the stopped page as it paints, in place of its image, and stays on for the worker's next stops until you turn it off. Your clicks, the wheel and your keys on the view go to the page. Esc gives the keyboard back to the tray, and Tab leaves the view unless a click into it took the keyboard. The frames go from the test's worker to the windows that watch that stop, the app's and Piwi Picker's Runs window, and nothing keeps them.

Pick on the image, or a Shift+click on the image or the view, names the element under the pointer: its locator shows under the test, with Copy.

Code to copy ​

The app holds no editor, so the code a stop makes comes to the tray, under Code from the runs, rather than into your file:

  • Assert a region picks a region of the page, once you watch a headless stop live: its ARIA snapshot becomes a toMatchAriaSnapshot check.
  • Mock a request lists the page's fetch and XHR responses, credentials hidden: the one you choose becomes a page.route, with what to review in it.
  • A locator picked, on the image or with the pause bar's Pick a locator, shows with the line it was picked for.

Each code shows the line it goes above, and its import lines apart, each with Copy. The code is made from the file as it is on disk, in the folder linked to the project.

Share live ​

A run that reports to your team's Piwi instance, as a Run locally in a folder whose .env or Playwright config names it does, can be shared there for a teammate to watch from its page, in a project whose live view is on: Share live, above the run's workers, any time while it runs. The first time since the app started, it says what goes out and to whom, and waits for your yes. Shared, the run says where and how many views are open, with Copy the run page's link and Stop sharing. A run that cannot be shared says why: Share a run from your machine.

A run that reports to the app itself (a reproduction, a bisect, a Run locally in a folder that names no instance) offers no Share live: the app hands out no live view key, since no teammate reaches it, and its project settings have no Live view section.

From Piwi Picker ​

Paired with the app, Piwi Picker's Runs window lists its runs beside your editor's, steers them, and watches their pages live. Code it starts at a stop of the app's run comes to the app's tray too.

For agents ​

The app's MCP server, which its MCP server page connects your coding agent to, serves these runs with the tools of Run control for agents: run_list, run_follow, run_control, page_snapshot, page_act, page_locator and code_write. An agent follows a run, pauses or steps it, reads the stopped page as its ARIA snapshot and acts on it by ref, as you can and no further: a stopped page alone, the actions the tools name, no code to evaluate. What comes from the page reaches it marked as the page's, never as instructions.

What it does shows in the tray: a stop it asked for says so (Paused by the agent), and so does its first action at a stop. The code code_write makes (the steps it took, an assertion, or a locator for the stopped line) comes under Code from the runs, to copy, and back to the agent in its answer: no file is written. A run nobody attends is not served, so an agent sees no Flake Lab run, bisect or lab job.

An agent pauses, steps or runs to a line only while the app's window is open, in the tray included: a headless stop goes on with no window to show it. A stop it asked for goes on two minutes after its last call, so a run never waits for an agent that left.

Limits ​

  • No recording. Record here, and Pick and Assert in the test's window, end in an editor: run the test from VS Code or a JetBrains IDE to use them.
  • A linked folder. A reproduction or a bisect step runs in a throwaway worktree, which no project links: its stops make no code.
  • A file changed since the run started makes no code: run the test again.
  • Run to cursor stays in the editor, which has the file.
  • One call at a time through the bridge. Claude Desktop reaches the app through piwi-desktop mcp-stdio, which passes its calls one by one: a run_follow or a run_control that waits holds the next call, 40 seconds at most (a 30-second wait, then the stopped page's snapshot).
