Scenario gaps & the Test Map ​

NeedsReporterCapture fixtures

The test catalog lists the tests you have. Scenario gaps describe the ones you don't: the route no test requests, the page nothing visits, the test that is the only thing standing between a page and no test at all. Each gap is a suggestion with its evidence and a next step, never a verdict.

Gaps come from the Test Map: one graph per project of what the application exposes (routes, pages, controls, links, and the handlers and dependencies behind them) and which tests reach each of them. It is built from what the reporter and the capture fixtures already record: the requests and page visits of every run.

Observed reach, not coverage. A gap says a test observably reached something, or that nothing did, measured from real runs, never from instrumented code coverage. "No edge" means "no evidence", not "proof of absence".

What a gap is ​

A detector reads the Test Map and the default branch's last 30 runs and reports one kind of gap: a route observed only with success statuses, a node exactly one test reaches, a new page no test reaches yet, a declared route nothing requests. Gap detectors & exposure lists every detector with its evidence. Each gap names its detector and its class:

ClassMeaningExample
blind-spotnothing reaches itObserved 412 times over the last 30 runs, always 200
false-comfortthe tests pass without checking it: a probe broke it, or the app logged an error, and they still passedTests pass when POST /api/orders breaks
fragilewhat reaches it could stop at any timeOnly checkout › coupon reaches this

Server probes add findings in two more classes, unhandled and degraded: the application itself did not cope with the fault, whatever the tests saw.

Gaps are ranked by exposure, a score from how often the code behind a node changes, whether it was part of an earlier escaped failure and the priority of the tests that reach it, and, for a changed file, how long it has been changing. The score and its factors show on every gap, and which gaps get which factors varies. Counts are per class, never a coverage percentage: a percentage over an observed surface looks complete exactly when that surface is sparse.

An uncovered change is a gap too, raised at pull-request time, and so is a page with open bug reports, and code no suite runs, error paths no suite runs, or code only one test runs.

The Coverage tab ​

The project's Coverage tab has three views. Gaps lists gaps and findings by feature, ranked, each with its class, score factors and evidence: the top 200 of the status picked, so a large map is read one status or one feature at a time. A gap on a file, a handler or a route names the files behind it with the lines the suites ran. Code is the combined coverage of a commit.

Map opens on the feature map: one circle per feature (from the piwi:feature tag), sized by the routes, pages and controls it groups, colored by its worst open gap, and linked to the features it shares nodes with. A feature also groups what its tests miss nearby, such as the controls on its pages, and a hub most tests reach links no features (how features group).

A feature, or a gap's node, opens in the feature graph: the node in the middle, what leads into it on the left, what it leads to on the right, nodes colored by class and edges by kind. The neighbors list under it has every neighbor; click a node to recenter on it. A file's coverage page opens it on the file's nodes, and a file or handler links back to its coverage. Agents walk the same graph with the get_feature_graph MCP tool.

Triage ​

Every gap takes the same four verbs as an inbox item:

  • Accept copies a draft test skeleton to your clipboard: a title from the gap, the piwi: annotations of the nearest test, the path from a reached page to the gap as steps, and a TODO where the assertion goes.
  • Snooze for a day, a week, or until the node changes.
  • Dismiss with a reason: not worth testing, covered elsewhere (which records the covering test as reaching the node), or wrong.
  • Covered by names the test written for it and closes the gap. A gap closed this way stays closed when its detector raises it again, and the covering test is recorded as reaching the node.

Gaps persist, so triage survives recomputation: a dismissed gap keeps its verdict, and a gap closes itself when the detector no longer finds it, for example once its node gains a trusted test. A closed gap is not always a test written: an uncovered change also closes when its file is deleted or nothing observes it any more. A gap on new surface stays open until a test reaches it (detectors). A closed gap that comes back reopens, unless it was closed with Covered by. Home lists the gaps still accepted a week after their acceptance: the tests not yet written.

Every verdict is also a labeled example that counts for or against its detector. A detector below 60% precision on a project with twenty or more verdicts mutes itself there (what muting changes).

The top new gaps of each project are the Gaps digestquality report; schedule it to your channels. Agents list, draft and triage gaps with the MCP tools, and the write-the-missing-test skill drives the loop.

What feeds the map ​

Every run adds the routes its tests requested on the application's own origin and the pages they ran locator calls on or ended on. Three optional sources add the rest:

  • The page inventory. With capturePageInventory on (off by default), the reporter records the controls and links of the pages a passing run visits. Control and link nodes, and the detectors that read them, appear only then.
  • Server spans. With the backend instrumentation for Nitro, each route gains the handler that served it and the dependencies that handler called.
  • The declared surface, below.

Declared surface ​

Beyond what tests observe, the map can hold what the application declares it exposes, so a route or page nothing reaches is named a declared, never hit blind spot instead of staying invisible. Three sources feed it:

  • The instrumentation's route manifest. The backend instrumentation serves the application's routes at /__piwi/manifest outside production, and the reporter uploads it with the run.
  • A committed manifest. A piwi.manifest.json next to your Playwright config ({ "routes": [...], "pages": [...] }) is uploaded whenever present, whatever the backend.
  • An OpenAPI URL, set per project under Project → Settings → Capabilities → Scenario gaps. Piwi reads the document when the URL is saved, every night and on a recompute, declares each path under the path of the document's first server (or Swagger's basePath), and records each route's documented response codes, so a success only gap can name the error codes a route documents but never returned under test. A route a later read no longer finds stops being declared.

A declared pattern is reached by every request it serves, as in a router: /blog/{slug} by /blog/hello.

Map health ​

Under the gap list, map health counts each input against what it could hold and names the detectors it wakes; an input that is short shows the step that fills it, so a quiet tab is not mistaken for a covered application.

What this is not ​

  • Not a test generator. A gap proposes a scenario; the assertion is yours.
  • Not a gate. Uncovered changes can only warn; see the gate flags.

The Test Map and its server probes are optional: decline either per project or for the instance, and these surfaces disappear.
